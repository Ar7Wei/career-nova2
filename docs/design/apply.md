# 投递分区 · 设计决策

> **投递分区**的设计文档。记这个分区**做了什么决策、做了什么设计、为什么这么设计**。
> 这里记细节与来龙去脉。术语定义见根目录 CONTEXT.md。

投递模块整体 = **职位聚合 + 投递执行 + 跟进** 三大块。**v1 只做「职位聚合」这块地基**；投递执行与跟进是长线线头。

---

## 1. 整体定位：发现 + 统一入口，用户保留决定权

**决策：投递模块不是"代投工具"，也不是"记录管理系统"，而是「职位聚合 + 半自动投递引擎 + 用户跟进」。产品哲学 = 帮用户探究需求、不替用户做决定（Grill 精神）。**

研究开源（get_jobs / Auto-JobHunter / jobfindsme）后的定位收敛：

- **不是全自动海投**（get_jobs 那类一天无差别打招呼）——违背我们的产品哲学，且 Boss 反爬军备竞赛打不起。
- **不是只记录**——不满足用户"帮它投出去"的初衷。
- **是"把岗位聚合过来 + 备好投递的一切 + 用户点最后一下"**——发现 + 统一入口 + 用户保留决定权。

**投递 = 两段分工**（用户原话定稿）：
- **应用负责**：抓岗位（聚合）+ 投递执行（半自动引擎）。
- **用户负责**：筛岗位（反馈）+ 跟进（聊了/为何拒/面试）。
- 岗位进来**先筛一遍**：用户对每条标"已投/没投/不匹配/不适合我/能力不到/忽略"——**筛选反馈是用户的地盘**。
- 已投的再跟进：聊了吗、聊了什么、为何拒、为何进面试、面试问啥、结果如何——**这些是长线线头，v1 只留钩子**。

---

## 2. v1 范围（阶段二）

**决策：v1 只做「岗位聚合」这块地基。投递执行、跟进、面试记录、定时抓取 → 全部线头。**

| 块 | v1 | 线头 |
|---|---|---|
| **岗位聚合** | ✅ 抓取 → 规范化 → 跨平台统一列表 | — |
| **岗位筛选反馈** | ✅ 用户标"已投/没投/原因" | — |
| **鲜活度排序** | ✅ liveness + 新鲜度 + 用户反馈过滤 | LLM 相关度打分 |
| **投递执行** | ❌ | 半自动引擎 + 用户在环 |
| **跟进** | ❌（留钩子） | 聊了/为何拒/面试/结果 |
| **抓取触发** | ✅ 手动「立即刷新」 | 定时/启动自动/后台即时 |
| **去重** | ✅ 同源幂等 upsert | 跨源聚合（不做） |
**等这块地基稳了，再逐条从线头拉出来。**

## 3. 来源适配器（connector）

**决策：每个招聘平台 = 一个 connector，`fetch_jobs(query) -> RawJobRecord[]`，把平台字段归一化成统一 schema。走两种路之一。**

| 路 | 做法 | 登录态 | 适配器成本 | 例 |
|---|---|---|---|---|
| **A. 免登录 JSON API** | 纯 HTTP 调平台的公开搜索 JSON API（seed 一下 session cookie） | 无 | 每平台一个 HTTP 适配器，省浏览器 | 猎聘 `api-c.liepin.com`（curl_cffi Chrome 指纹） |
| **B. Electron 隐藏窗口读 DOM** | Electron 隐藏 `BrowserWindow` 加载搜索列表页、复用登录态、读 DOM 抓岗位卡片 + 跳转 URL | 隐藏窗口内登录一次（平台登录快捷入口） | 每平台一套选择器 | 前程无忧（`.bmsg.job_msg` 读 JD） |

> **常见误解**：路 B 曾经设想为「CDP 授权浏览器（用户授权的本地 Chrome CDP 会话）」，实测后改用 **Electron 隐藏窗口 + 读 DOM**（`electron/services/job-scraper.js` → `POST /jobs/ingest`）。投递详情窗口才是 `WebContentsView`（`electron/windows/apply-window.js`），两者别混。

- **v1 connector = 猎聘（免登录 API，curl_cffi Chrome TLS/JA3 指纹，实测 ~1s 返回 40 条，2026-08-13 验证）+ 前程无忧（Electron 读 DOM）。** **BOSS 抓取已砍（2026-08-31，§8⑦）**——无限滚动自动化打不通 + 登录态易失效 + 投递方式是「先沟通」而非「投简历」，只做猎聘 + 前程无忧两家。
- **智联已放弃（2026-08-13 实测 + jobfindsme 实盘报告）**：`fe-api.zhaopin.com/c/i/sou` 返回 `numFound=999999`（假值）+ 空 results——免登录 API 被风控拦截，详情页再撞 Security Verification 墙。**connector 已删（2026-08-31）**；风控只会更严，真要回头从 git 历史翻。方向修正：从"智联先行"改为"猎聘先行"，最终智联出局。
- **关键洞察：不是"要不要爬"的二元，而是"能免登录走 A 的走 A，必须登录的走 B"。**（架构借鉴 jobfindsme，它 MIT 协议、Python，作参考实现，不直接 import——我们本地单用户桌面应用，自己实现、守分层与错误契约。）
- **岗位数据归一化成统一 schema，用户保留决定权**（CONTEXT.md「来源适配器」）。
- 聚合是反爬最先打的地方（高频只读行为，最易触发限流/验证）→ 只能登录态 + **低频手动抓**（见 §8 触发）。

> **实现（2026-08-13）**：猎聘 connector（`app/connectors/liepin.py`）。猎聘用 curl_cffi 的 `impersonate="chrome"`（普通 httpx 被软屏蔽）——`uv add curl_cffi`。智联 connector（`app/connectors/zhilian.py`）曾写好、风控识别已验证，**2026-08-31 删除**（已放弃）。

## 4. 数据模型

**决策：两表分离——客观生死（程序管）与主观反馈（用户管）不揉一个 status。字段不强归一。**

### `jobs`（一条 = 一个平台的源岗位）

平台返回什么存什么；去重靠 upsert。**跨源不做去重/聚合**——同一岗位在猎聘和前程无忧都出现就是两条，用户想投哪个平台投哪个；特别心动的**多多益善**（只要每条能投出去，§5）。

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK | 自增 |
| `source_name` | TEXT（index） | 平台：`liepin` / `job51`（`boss` 已砍 2026-08-31，§8⑦） |
| `external_id` | TEXT | 平台岗位 ID；与 `source_name` 组合唯一 |
| `title` | TEXT | 职位名 |
| `company` | TEXT | 公司 |
| `city` | TEXT | 城市（原始字符串，不强归一） |
| `salary_text` | TEXT | 薪资（原始字符串，不强归一） |
| `experience` / `degree` | TEXT | 经验 / 学历 |
| `skills` / `job_labels` | TEXT | 技能 / 标签 |
| `company_scale` / `company_stage` / `company_industry` / `welfare` | TEXT | 公司规模 / 阶段 / 行业 / 福利 |
| `source_url` | TEXT | 岗位详情页 URL |
| `apply_url` | TEXT | 投递入口 URL（投递引擎/跳外部用） |
| `liveness` | TEXT（index） | `active` / `stale` / `closed` / `unknown`（程序更新） |
| `platform_updated_at` | TEXT（可空） | 平台发布/更新时间；有的平台不公开，可空 |
| `last_seen_at` | DATETIME | **我们自己的抓取时间，恒有**——新鲜度排序的地基 |
| `created_at` / `updated_at` | DATETIME | 时间戳 |

唯一约束：`UNIQUE (source_name, external_id)` —— 同源幂等 upsert。

### `job_screening`（一条 = 用户对某条岗位的反馈）——**已作废（2026-08-30，见 §12）**

> ⚠️ 下表是 v1 历史设计，**已被 `job_followup_events` 状态线取代**（§12）。保留在此仅为记录决策来龙去脉，非现状。作废清空、不迁移。

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | INTEGER PK | 自增 |
| `job_id` | INTEGER（index，外键 → `jobs.id`） | 被反馈的岗位；一条岗位最多一条反馈 |
| `applied` | BOOLEAN（默认 false） | **`投了` / `没投` 二元**——投了 → 进入追踪（follow-up，线头）；没投 → 可选原因 |
| `reason` | TEXT（可空） | 没投的原因枚举：`mismatch` 不匹配 / `not_suitable` 不适合 / `underqualified` 能力不到 / `wrong_push` 错误推送 / `duplicate_push` 重复推送 / **`closed` 已关闭**（用户确认该岗位已关闭） |
| `note` | TEXT（可空） | **自定义原因 / 备注**（自由文本） |
| `created_at` / `updated_at` | DATETIME | 时间戳 |

设计要点：
- **筛选反馈收敛为二元**（2026-08-13 用户定稿）：`投了`/`没投` + 没投的原因（预置枚举进 `reason`，自定义文字进 `note`）。"投了"只是标记（进追踪的钩子），追踪/统计本身线头。
- **用户反馈存独立表**，跟岗位走（`job_id` 外键）——upsert 只更新岗位字段，**不动用户反馈**（§5 增量）。
- **feedback 不存成 user_facts**：fact 是"对用户的了解"，岗位是"外部世界的一条机会"，语义不同。**用户求职动作沉淀成 fact 已砍（2026-08-31）**——投递页已有更具体的设计（状态时间线），这条旧线头过时。

**字段策略**：
- **薪资/城市等存原始字符串**（`salary_text`/`city` 原样）——不做强归一化（画蛇添足，砍掉）。
- **`platform_updated_at` 可空 + `last_seen_at` 恒有**——新鲜度排序靠 `last_seen_at` 兜底；平台发布时间拿到是加分信号（能看出岗位挂多久），不能拿它当地基。

## 5. 去重与增量

**决策：只做同源去重；跨源不去重；增量 = upsert 不动用户反馈。**

- **同源去重**：`UNIQUE(source_name, external_id)` 幂等 upsert。落地 URL 是平台岗位 ID 的**封装/载体**——同源去重用 URL 与用 ID 是同一件事，`external_id` 取 ID、`source_url` 是它的派生。
- **跨源不去重**（用户拍板）：同一岗位在猎聘和前程无忧都出现就是两条，用户想投哪个平台投哪个；特别心动的**多多益善**（只要每条能投出去）。**也不做跨源语义聚合/合并**（砍掉，不做）。
- **增量**：upsert 只更新岗位字段（liveness/薪资/时间），**不动用户反馈**——今天抓过的岗位，明天 upsert 后仍是同一条，用户反馈还在；列表只标记**新增**（`is_new`）和**生死变化**（closed 灰显），不重新铺一遍。

## 6. 排序与筛选（**2026-09-08 收敛**）

> **本节已随排序收敛重写。** 旧版（「排序维度：鲜活度/时间/相关度 + 平台筛选，均进 v1」）已废——**相关度与平台筛选都砍了**：相关度依赖 `GET /jobs?query=`，而前端从无搜索框、从不传 query，是死维度；平台筛选前端下拉已删。详见 §12.11 与 。

**决策：全 tab 只留「时间」一个排序维度，每 tab 一个语义时间键；日期范围筛选与排序共用同一键。**

| 项 | 现状 |
|---|---|
| **排序维度** | **只剩「时间」**（`followup`），全 tab 复用；鲜活度 / 相关度两维度已砍（2026-09-08） |
| **语义时间键** | 未处理 = 收录时间 `last_seen_at`；已投递 = 投递时间；录用 = 录用时间；不再追踪 = 处理时间（后三者 = 当前态事件的 `at`）。排序与日期范围筛选**共用同一键** |
| **排序控件** | 统一为 `[语义时间文字标签] [时间范围筛选器（固定宽度）] [正倒序箭头]`，四个列表 tab 复用、只换前缀标签词 |
| **日期范围筛选** | 天粒度闭区间，落地 |
| **平台筛选** | **已删**（2026-09-01）——前端不再有平台下拉，列表恒全平台 |
| **相关度** | **已下线**（2026-09-08）——曾是字段级关键词匹配，因前端不传 query 退化成鲜活度，是死维度。检索关键词未来从简历+事实库提炼（线头），届时作为**新排序维度**重新加入 |
| **LLM 打分** | **已砍**（2026-08-31）——除猎聘外不打开详情页拿不到详情，无从匹配 |

- **面试 tab 无此控件**——它是纯日历编年（§12.10）。

## 6bis. 岗位关闭真相源

**决策：岗位是否"关了"的有效状态 = 用户确认关闭（权威）+ 平台 liveness（候选信号，暂不可信）。灰度可见；演进式收敛。**

- **平台 liveness**（`jobs.liveness`）= 程序爬的**候选信号**，可能错 → 关了的**灰度可见**（不藏，防误伤）。
- **用户确认关闭** = 用户点进岗位确认关了，在**详情外框头部**（"眉头"）标「关闭」——**权威真相源**。
- **演进**：等平台字段被验证可信（所有平台可依赖）→ **真相源收敛到平台字段**，平台说关了的直接藏掉。**灰度 = 候选信号不可信；藏掉 = 可信/用户权威确认**。

## 7. 投递执行（线头，但地基已探明）

> ⚠️ **本节含大量已作废平台的实现细节（BOSS / 智联 / 拉勾），保留作历史与教训，勿当现状读。** 平台已于 2026-08-31 收敛为**两家：猎聘 + 前程无忧**（BOSS 彻底砍、智联与拉勾放弃）。现行抓取机制见 **§8**（事件驱动 + 续页游标 + 单平台三态）；§7 这几节的价值在「踩过的坑」——探测器耍靠结构选择器不靠文案（§7.3 铁律）、`will-navigate` 误伤二次导航（§7.8bis）、登录态探测不能用 cookie 标志（§7.8）。其中 WebContentsView 结论现用于**投递详情窗口**（`electron/windows/apply-window.js`），**抓取**已改用隐藏 `BrowserWindow` 读 DOM（`electron/services/job-scraper.js`）。

**决策：v1 不做投递执行，留线头。但投递执行的技术方案已定（WebContentsView + 人在环内阶梯），并通过猎聘 spike 验证了地基。方向 = 应用内置浏览器驱动 + 「切到外部」逃生舱。**

### 7.1 技术底座：WebContentsView（不是 `<webview>` tag）

Electron 官方**明确不推荐 `<webview>` tag**（正经历影响稳定性的架构变更，未来不可用）；官方推荐 `WebContentsView`（主进程创建、`executeJavaScript` 直读直写第三方 DOM、独立 `session` 持久登录态、`did-navigate` 观察跳转、独立进程崩溃隔离）。**投递执行 = "读、写、观察"第三方页面 → 只能用 WebContentsView；iframe 只能"看"（跨源隔离封死读/写通道），当前 v1 用 iframe 展示详情够用，投递执行时换成 WebContentsView。**

WebContentsView 的核心代价 = 主进程专属 + 手动 `setBounds` 定位（与渲染进程协调）——这决定了它**不做成 Mantine `<Modal>` 里的元素**，而大概率是独立原生窗口或主窗口里主进程划定的固定区域（届时按投递交互形态定）。

### 7.2 人在环内的四档降级梯子（自动 ≠ 被反爬掐死）

**自动投递的风险不在"自动"，在"是否用爬虫手段"。WebContentsView = 真浏览器 + 真登录态 + 人接关键点，是把风险压到最低的自动方式。** 同一块地基，自动程度是逐档降级的梯子，引擎撞到墙就往下踩一档：

| 档 | 命名 | 谁驱动 | 观察（反馈收集） | 何时启用 |
|---|---|---|---|---|
| 3 | **全自动** | agent 驱动填表/点按钮 | agent 自动记"已投递" | 平台探测器稳定、无墙 |
| 2 | **半自动** | agent 驱动，撞到验证码/风控 → 弹出让人接 → agent 继续 | agent 自动记 | 需要登录/验证码配合 |
| 1 | **手动-观察** | 人驱动，agent 被动观察（URL 跳转/网络/DOM） | agent 自动记"已投递" | 自动化被识破（页面能渲染但脚本失效） |
| 0 | **手动-外部** | 外部真实浏览器，人全手动 | ❌ 全丢，用户手标 | 页面都渲染不出（失败模式 A） |

- **降级是动态、逐档、每平台独立的**（猎聘还在档 3，BOSS 掉到档 1，互不影响）。
- **"控制"与"观察"可分离**：平台封了"控制"（脚本注入被拦），"观察"往往还活着（页面渲染/URL 跳转/网络请求）——所以档 1 不是安慰剂，是同一套观察能力的复用。
- **失败模式 A（连页面都渲染不出 = 封 Electron UA/指纹）才是地板**：只能退档 0（外部浏览器 + 用户手标）。B（页面正常、脚本被识破）几乎无损退档 1。

### 7.3 探测器配置（每平台一份，猫鼠游戏的固定成本）

自动投递要靠每平台一份**探测器配置**：投递按钮选择器、成功信号（URL/网络/DOM 特征）、已知墙（验证码/风控选择器）。平台改版它就会失效——这是躲不掉的固定成本，但它只决定**自动到哪一档**，不影响**退回观察档**。

**铁律（spike 教训）：不能靠猜文案关键词定位，要靠结构选择器（类名）定位，文案只做二次确认。** 反例：探测脚本预设"投递/投个简历"关键词，漏了猎聘真实文案"**投简历**"（少一个字就漏）；而类名 `a.btn-minor` 稳定命中。

### 7.4 验证阶梯（先探明地基，再谈自动）

**决策：每接入一个平台，按三级阶梯逐级验证，任何一级不过就不往上走，避免大面积实现后才发现地基不牢。**

| 级 | 名称 | 验证什么 | 风险 |
|---|---|---|---|
| 1 | **能看得到** | WebContentsView 能否渲染岗位页（失败模式 A 存不存在：白屏/跳登录/被拦） | 无（只 load） |
| 2 | **能捕捉到** | `executeJavaScript` 能否读到 DOM（标题/正文/投递按钮/墙关键词） | 无（只读） |
| 3 | **能点得动** | 注入的点击能否触发平台事件（React 合成事件坑；用"收藏"等无害动作测） | 无（不真投） |
| （4） | 真投一条 | 全自动投递到底成不成 | **真投，需登录态 + 谨慎，单独开** |

### 7.7 收编：独立投递窗口（2026-08-17）

**决策：级 1 + 级 2 已验证 → 收编为真实功能：岗位详情改由「独立投递窗口」承载（不再 iframe）。** 投递引擎（预填/点投递/捕捉反馈）等级 3 + 真投测完再接入。

**关键判断：独立窗口形态下不需要 WebContentsView。** WebContentsView 唯一理由是把第三方页面嵌进另一窗口与其他 UI 排布（spike 里与左侧控制面板并排），需要手动 `setBounds`。独立 `BrowserWindow + partition` 就拿到全部投递执行能力（`executeJavaScript` / `did-navigate` / 独立登录态 / 崩溃隔离），且省掉 setBounds 这个最大的坑。

- **每平台独立持久 partition**（`persist:careernova-{source}`）：登录态各存各的、互不串味、重启不丢（spike 已暴露共享 session 会串味的隐患，收编时修正）。
- **同平台复用窗口**：再点同平台岗位，复用窗口切换 URL，不重复开窗。
- **前端入口**：详情弹窗「应用内打开」按钮 → IPC `apply:open-detail` → 独立窗口；浏览器 dev 退化 `window.open`。
- 落地：`electron/windows/apply-window.js`（窗口 + IPC 注册）、`preload.js` `openJobDetail`、`ApplyPage.tsx` 去 iframe 换按钮、`desktop.d.ts` 类型、i18n 新键。

- **「切到外部」逃生舱**：用户在外部默认浏览器已登录的平台（Boss 等），直接切过去用现成登录态，不强制在应用内重登（= 档 0 的落点）。
- **只有「已投递」能由应用确证**（且仅在内置浏览器路径）；「已通过/已拒绝」平台不暴露给第三方，**只能靠用户配合 + 应用排跟进提醒**（"3 天后去查已读/回复"）。
- **邮件直投已砍（2026-08-31）**：官网信息不迭代、邮件不回应、很多公司没官网——邮件是下策。

### 7.7bis 坑：`will-navigate` 导航拦截误伤第三方窗口（2026-08-18）

**现象**：前程无忧详情页「应用内打开」恒白板，且 JD 抓取恒 `bodyLen:0`——即便间隔 10 分钟重试依然白板（不是限流）。BOSS/猎聘正常。

**根因**：`main.js` 的 `web-contents-created` 对所有 webContents 挂了 `will-navigate` 拦截（本意是防主窗口 dev 模式下导航离开本地 dev server）。前程无忧详情页加载后会**往 URL 追加 `?timestamp__1258=…` 参数做二次整页导航**来拿真实内容，这次导航被 `event.preventDefault()` 拦掉 → 页面卡在空壳 → 白板。BOSS/猎聘是 SPA 用 `history.pushState` 改地址，不触发 `will-navigate`，所以不受影响。

**教训**：
1. **`web-contents-created` 是全局钩子**，会命中所有窗口（主窗口 + apply-window 第三方页 + 登录窗口）。挂 `will-navigate` 拦截必须**按 webContents 身份过滤**——只拦「当前 URL 是本地前端」的窗口（主窗口），放过第三方岗位页。修复：`will-navigate` 回调里先 `webContents.getURL()` 判断，非 `http://127.0.0.1` 起头的（第三方页）直接 return 放行。
2. **「应用内打开第三方页白板」先查 `navigation_blocked` 日志**——别急着归因到限流/风控/登录态。本次走了弯路（误判限流、误判登录态、误判 body 检测时机），最后一条 `navigation_blocked` 日志一锤定音。

### 7.8 岗位抓取·读 DOM 路线（2026-08-17）

**决策：BOSS/智联/前程无忧的内部 JSON API 全被风控，改走「真浏览器渲染列表 → 读 DOM」路线；拉勾放弃。**

**背景（spike 实测 + 对照 jobfindsme 实盘）**：三家内部 API 全碰壁——
- BOSS `wapi/zpgeek/search/joblist.json` 返回 `code=37 您的环境存在异常`（要 JS challenge 算签名）；
- 智联 `fe-api.zhaopin.com/c/i/sou` 返回空信封 `numTotal=0`（风控）；
- 前程无忧 `we.51job.com/api/job/search-pc` 被阿里云 WAF（返回 HTML challenge）。

这些风控拦的是「非浏览器的 API 请求」，但拦不住「真浏览器把页面渲染出来给人看」。故**不爬内部 JSON API，改用隐藏 `BrowserWindow` + 复用 `persist:careernova-{source}` 登录态，导航到搜索列表页，等 SPA 渲染，`executeJavaScript` 从 DOM 读岗位卡片**——与 §7.7 独立投递窗口同一套能力，只是对象从详情页换成列表页。

**实测四家字段映射（结构选择器，全部 class 定位）**：

| 平台 | 卡片 | 标题 | 薪资 | 公司 | 城市 | 跳转 URL |
|---|---|---|---|---|---|---|
| 猎聘 | （HTTP 快路径，不走 DOM） | — | — | — | — | `liepin.com/job/{id}.shtml` |
| BOSS | `li.job-card-box` | `a.job-name` | `span.job-salary` | `a.boss-info` | `span.company-location` | `a.job-name` href |
| 智联 | `div.joblist-box__item` | `a.jobinfo__name` | `p.jobinfo__salary` | `a.companyinfo__name` | `div.jobinfo__other-info-item`[0] | `a.jobinfo__name` href |
| 前程无忧 | `div.joblist-item` | `span.jname` | `span.sal` | `span.cname` | `div.area` | 卡片无 href，从 `sensorsdata.jobId` 拼 `jobs.51job.com/all/{jobId}.html` |
| 拉勾 | ❌ 搜索页登录后才渲染、无标准岗位链接 | — | — | — | — | — |

**详情页分平台（Electron 实测，2026-08-17，2026-08-18 修正）**：
- **BOSS**：详情页可**直接冷开**（`a.job-name` href 即真实详情 URL，无反爬墙）→ 读 `.job-sec-text` 拿 JD。
- **前程无忧**：主列表卡片无 href，但 `sensorsdata.jobId` 能拼通用详情 URL `jobs.51job.com/all/{jobId}.html`（实测可冷开、无墙）→ 读 `.bmsg.job_msg` 拿 JD。**JD 异步加载慢**：`did-finish-load` 后需 settle ≥5.5s 才能读到（3.5s 读不到空）。详情页加载后会有一次追加 `?timestamp__1258=…` 的二次导航（见 §7.7bis，被 `will-navigate` 误拦会白板）。
- **智联**：详情页**冷开/点击都撞 Security Verification 墙**（跟登录态、参数都无关，是平台对「脱离搜索 session 直接开详情」的反爬）→ **放弃智联**（2026-08-17 用户拍板）。

**详情页偶发失败兜底（2026-08-18）**：前程无忧详情页对连续高频请求会偶发 `bodyLen:0`（整页空，loadURL 不报错）或 `ERR_FAILED(-2)`。抓取侧 `readDetailJd` 对 body 空做退避重试（最多 2 次）；窗口侧 `did-fail-load` 对 `ERR_FAILED(-2)` 做一次退避 reload。这些是「限流是间歇的」的应对，与 §7.7bis 的导航拦截（稳定必现）是两回事，别混。

**登录入口（2026-08-17，2026-08-18 修正）**：投递页顶栏加平台登录快捷入口——解决「不登录抓不到岗位、没岗位又没法登录」的死循环。入口 = 打开各平台登录页的独立窗口（复用 `openJobDetailWindow` + partition 登录态）。**已登录则不弹窗**（`apply:open-login` 先导航探测，已登录返回 `loggedIn:true`，前端直接标绿）——否则已登录用户点入口又见登录表单，误以为"没登录"。

**登录态检测（随用随测，2026-08-17，2026-08-18 修正）**：不做轮询、不用「有 cookie」判断（任何访问都种 cookie，恒真；且 BOSS 登录后 `wbg` 仍为 0、猎聘登录后 `liepin_login_valid` 仍为 0——**cookie 标志不可靠，会假阴性**）。改为**导航探测**——隐藏窗口访问一个「必须登录才能停留」的页面，看最终 URL 是否被甩到登录页：
- BOSS：访问搜索页 `web/geek/job?query=…&city=…&page=1`（**必须带 `page=1`，与抓取 URL 一致**；不带 page 未登录不跳登录页，会假阳性），未登录被甩到 `web/user/`（登录页）。
- 前程无忧：访问 `we.51job.com/pc/my/myjob`（我的投递），未登录被甩到 `login.51job.com`。
- 猎聘：访问 `liepin.com/user/`，未登录跳回首页。

**登录成功检测（2026-08-18 修正）**：不能用 `origin` 变化判断——BOSS 登录前后同 origin（都在 `zhipin.com`），永远判不出；且 BOSS 登录页是 React SPA，登录成功是**页内跳转**（`did-navigate-in-page`），不触发整页 `did-navigate`。修正为：`did-navigate` + `did-navigate-in-page` 双监听，用**登录页 URL 的 path 特征**判断跳离（`/login/`、`/web/user/`、`login.51job.com`），跳离即登录成功 → `apply:login-changed` 推前端 + 关窗。BOSS 登录后可能 URL 僵在登录页不跳，此时靠用户手动关窗（cookie 轮询不可靠，已弃用）。

**翻页（2026-08-17）**：当前页新岗位不足 `PER_SOURCE`（5 条）时自动翻下一页（BOSS `&page=` / 前程无忧 `&pageNum=`），最多翻 `MAX_PAGES`（3）页——让增量抓取闭环（否则第一页新岗位抓完后刷新就永远 0 条）。

**架构落地**：
- 抓取迁到 Electron 主进程（BOSS 必登录，登录态只在 Electron）→ `electron/services/job-scraper.js`（读 DOM 列表 + 详情冷开读 JD → POST 后端 `POST /jobs/ingest` 入库）。
- 猎聘保留后端 HTTP 快路径（curl_cffi，~0.9s、免登录、已验证）——不动。
- 前端刷新 = 并行「后端猎聘 HTTP + Electron 读 DOM 两家（BOSS/前程无忧）」，合并 added/updated。单家失败不拖垮其余。
- **增量去重**：复用 `jobs` 表 `UNIQUE(source_name, external_id)`——抓取前查 `GET /jobs/external-ids` 拿已抓集合，只开没抓过的详情，两次刷新天然不重复。**每平台限 5 条**（先硬编码，后期放设置面板）。
- **JD 入库**：`jobs.description` 存详情页 JD 正文（BOSS/前程无忧有，智联已放弃），前端详情弹窗展示。
- 拉勾放弃（与 jobfindsme 退役 `lagou_cdp` 判断一致）。

**诊断脚本（`electron/scripts/`，2026-08-18；`probe-*.js` / `cdp-*.mjs` 已于 2026-09-11 清扫删除）**：平台反爬排查用的一次性诊断脚本（`probe-detail.js` / `probe-click-through*.js` / `probe-job51-link.js` 等）**已删**——用完即弃，平台改版后需重测选择器时按需重写。保留 `diagnose.js`（进程诊断）与 `kill-verify.js`（必杀路径验证）。**重写/再跑这类脚本时注意两点**：① 不要用 bash `timeout` 强杀（会留僵尸 electron 子进程锁 partition cache，日志报 `Unable to move the cache`）——脚本自身 `app.exit(0)` 正常退出即可；② 脚本没做 `app.setPath("userData", …)`，会用默认 userData（`career-nova-electron`）而非正式 app 的 `Career Nova`，读到的 partition 登录态与正式 app 不通——跑前需补 `app.setPath("userData", path.join(app.getPath("appData"), "Career Nova"))` 才能测真实登录态。

## 8. 抓取触发（2026-08-31 定稿重构：事件驱动 + 续页游标 + 单平台三态，两平台：猎聘 + 前程无忧）

> 原 §8「手动『立即刷新』+ 后台轮巡」于 2026-08-31 grill 收敛为下面的**事件驱动 + 续页游标 + 单平台三态**设计。**已落地（2026-08-31 Task #7）**，本段是完整规格 + 实现后的补充（翻页真相 ⑦ 已实测，实现决策另见 「实现决策」段）。
>
> 核心原则：**零计时器**——爬虫只被用户事件叫醒，醒来的那一刻才惰性看钟（throttled/exhausted 都靠"事件到来时看钟"），不用 setTimeout/setInterval 主动唤醒。反爬的正解是「事件驱动的两脚之间天然就是人速」，不是「低频定时」。

**① 废 15min 轮巡，改事件驱动（用户动作触发）+ 三层去重**：
- 触发点全集（`maybeKick()` 只在这几处调）：
  1. **推进岗位成功**（pushFollowup / scheduleInterview 等让 `unprocessed` 变化的动作）→ 走**跃迁检测**；
  2. **改方向 commit 后**（游标已重置、新方向立刻有货，值得踢一次）；
  3. **进入投递页**（在场即踢，受 `should_crawl` 门控——顺手解冷启动：apply_mode 开、backlog=0、应用常驻托盘时，进页面就是叫醒事件）；
  4. **开「求职之路」开关**（apply_mode 关→开）。
- **跃迁检测去重**（治"切 tab / 改排序 / 改筛选都 `refreshList`"的 UI 抖动）：`maybeKick()` 记一个"是否已处于该踢状态"布尔，只有当 `unprocessed` **从 `≥ 触发值` 向下跃迁到 `< 触发值`**（或首次进入该踢状态）时才真发一次 kick；之后连续拿到同样的 `unprocessed=0` 只有第一次触发。
- 三层去重（全程零计时器）：前端跃迁检测（去 UI 抖动）→ Electron `kickCrawl` IPC 的 **re-entrancy 闸**（爬虫在跑就跳过，去并发）→ 后端 `should_crawl`（去"不该爬"）。
- 触发值 = 保留的未处理底仓，**默认 5**（≤ 触发值就补；不是"清零才补"，避免空仓 + 避免 exhausted 转天解禁时缺那次踢）。

**② 每平台独立 quota + 续页游标（废"从第 1 页重爬"）+ 统一后端记账**：
- 设置里每平台 `quota`（每轮抓几个新岗）+ `cap`（每轮最多扫几页，**一个数，用户手动调**）。
- 抓一轮从该平台**游标页续爬**（非第 1 页），爬到凑满 quota 或撞 cap 或空页；external_id 去重只捡新的。
- **游标是二维的 `(组下标, 组内页号)`**：方向是 `keywords: list[list[str]]`，每个查询组各自独立搜索、各有自己的第 1..K 页，没有"合并后的扁平页号"。**组间顺序消费**（组 1 的 1..cap 走完再轮到组 2），与 §11.2「lazy——凑满批大小就停，后序组只在前面组抓干后轮上」一致。
- **「页」是两平台各自翻页机制的游标**（见 ⑦ 翻页真相）：猎聘 `currentPage` 整数（POST 直调）；前程无忧翻页器触发的 XHR `pageNum`（游标 = 下一次 XHR 的 pageNum）。游标统一记「每平台当前翻页游标」，推进 = 触发下一次请求。
- **统一存后端 SQLite `crawl_state` 表**（唯一真相源，跨 app 重启、跨天不丢）。猎聘（后端 HTTP）与前程无忧（Electron 读 DOM）两边**只报结果**（`GET /jobs/crawl-state` 读游标决定从哪组哪页开始、`POST /jobs/crawl-state` 上报一轮结果），后端据此推进游标 / 标 throttled / 标 exhausted——**记账统一在后端**，限流信号在哪产生就在哪归类。DOM 侧的 `ok=false`/`bodyLen=0` 归 `throttled`，猎聘侧 `LiepinBlockedError` 归 `throttled`。
- **两重置**：改方向（`commit_direction` 落库时**显式重置**游标 + 清 exhausted/throttled 标记）与核爆（`crawl_state` 当求职数据随 reset 一起清空，不归"配置保留"）都让游标归零——游标是「方向 × 数据」的派生进度，任一输入变了进度就没意义。

**③ 单平台三态（fresh / throttled / exhausted）**：
- `fresh`（有新增）→ 正常，游标前进。
- `throttled`（被限流：猎聘 `LiepinBlockedError`、DOM `ok=false`、job51 `bodyLen=0`）→ 别当抓干，记**失败时间戳 + 惰性冷却比对**（默认 15 分钟硬编码，与 exhausted 同构、一个机制两种单位）——下次 kick 时看"距上次失败 < 冷却期"就跳过。**不靠事件计数退避**（限流恢复是墙钟时间，跟处理几个岗无关）。
- `exhausted` = **空页/到底**（该次查询没有新的可抓：猎聘空 jobCardList、前程无忧翻到空页），**不是「0 新岗」**——「有卡片但全被 external_id 去重」≠ 到底，游标继续前进（后面可能还有新的）。按**日期**打标记，当天跳过这家（转天 kick 惰性比对日期无标记就放开）；本轮继续爬剩下的平台（各平台独立，不互相挤占）。

**④ 深爬 / 稳态 = 同一个循环，不是两个阶段（废阶段机）**：
- 每轮 = 同一个操作：从游标开始、最多扫 cap 页、凑够 quota 就停、去重、推进游标。
- 两个终局条件**都「回第 1 页」**，不是切换阶段：**空页** → exhausted（记日期、当天跳过、转天回第 1 页重查）；**撞 cap**（后面还有货）→ 游标回第 1 页，下一轮继续从前面扫。
- 「深爬 → 稳态」是**同一个循环跑出来的自然现象**：库里空时游标从第 1 页往后走、每页都是新岗（看着像攒量）；游标绕满一圈回到第 1 页后，去重滤掉老岗、只剩真正新帖（看着像盯新）。**无阶段存储、无过渡事件**，`crawl_state` 里没有 phase 字段。
- 代价（接受）：市场安静、没有新帖的那一轮，会白扫 cap 页（去重全滤掉、不是空页、凑不满 quota）——事件驱动 + 低频，偶尔一次 cap 请求，不致命。用户想省就手动把 cap 调小。

**⑤ 废手动刷新按钮**：岗位只来自事件驱动的后台爬。猎聘读方向已落地（Task #6），废手动后猎聘路径自动吃方向。**与 §12.11③ 冲突处以本段为准**——严格门控，无「无视 backlog 强行抓」的逃生舱。

**⑥ 设置 UI**：「求职之路」开关旁一个「详细设置」按钮，点击展开——每平台 quota + 全局触发值（cap 待翻页问题解决后再决定进不进 UI，见 ⑦）。

**⑥bis 指示器化（2026-09-01 grill 定稿）**：投递页顶部栏加一个**常驻「求职之路」指示器**（跨 tab，面试 tab 除外），点它弹设置弹窗——原检索控制台 `ApplyModeBar` 的**全部内容**（总开关 + backlog + 每平台 quota + cap + 触发值）迁入此弹窗，指示器成为「求职之路」唯一入口。原检索控制台浮窗删掉「职位获取」模块，只剩检索条件 + 登录平台。
- **三态**（关 = 归「没跑」）：`running`（绿转圈，一次 kickCrawl 在途）/ `受限`（黄点，tooltip 细分「限流中」vs「今天已爬完」）/ `idle`（灰点，空闲或 apply_mode 关）。优先级 running > 受限 > idle。
- **信号合成**：`running` 来自前端 `applyStore.kickRunning`（把模块级 `kickInFlight` 提升为响应式）；`受限` 复用 kick 返回值——后端 `KickResponse` 新增 `gate_reason` 字段（`crawled`/`apply_mode_off`/`no_direction`/`backlog_full`/`throttled`/`exhausted`），门控拒时带出原因，区分「受限（throttled/exhausted）」与「backlog 满」（否则两者在返回里都 `null` 长得一样）。**零轮询、零新端点、零计时器**——信号只在每次 kick 完成时更新，守住事件驱动铁律。

**⑦ 翻页真相（2026-08-31 实测）**：
- **抓取平台收敛为两家：猎聘 + 前程无忧（BOSS 砍掉，见下）**。翻页机制各异，但本质都收敛到「一次请求的参数」，游标统一记「每平台当前翻页游标」、推进方式 = 触发下一次请求：
  - **猎聘**：HTTP `currentPage` 0/1/2/3 各 42 条、零重叠 → ✅ 真分页（`scripts/probe_liepin_paging.py`）。
  - **前程无忧**：**点翻页器 `.el-pagination .btn-next` → 触发 XHR** `GET /api/job/search-pc?api_key=51job&timestamp=…&keyword=…&pageNum=N&requestId=…&pageSize=20&pageCode=…&scene=7`，点「下一页」后 jobId 与第 1 页 **0 重叠** → ✅ 真分页。**注意**：`pageNum` 在 XHR 的 query 里，不在页面 URL——改页面 URL 的 `pageNum` 不翻页（这是之前误判「恒吐第一页」的根因）。
- **BOSS 抓取已砍（2026-08-31）**：BOSS 翻页 = 无限滚动（左栏容器滚动触发 XHR），但隐藏窗口下 `scrollTo`/`sendInputEvent` 均无法触发其滚动监听、自动化打不通；登录态在反复探测中失效；BOSS 投递方式也是「先沟通」而非「投简历」（与两家主源不一致）。收益低、成本高 → 只做猎聘 + 前程无忧。现有 `job-scraper.js` 的 BOSS 路径（`SOURCES.boss` + `&page=` 翻页 + `.job-sec-text` JD）在 Task #7 里一并删除。

## 9. 验证投递成功（Q11 分工）

**决策：「已投递 / 已通过 / 已拒绝」哪些能捕捉、哪些要用户配合——**

| 状态 | 应用能否捕捉 | 怎么得到 | 谁驱动 |
|---|---|---|---|
| **已投递** | 能（内置浏览器时） | 投递动作后应用检测"投递成功"标记（DOM）→ 自动确认 | 应用确证（半自动） |
| **已投递** | 只能用户标记 | 逃生舱/外部投了，应用看不见 | 用户 |
| **已通过**（面试/笔试/邀约） | 不能捕捉（平台不暴露） | 用户手动更新 + 排跟进提醒 | 用户 |
| **已拒绝** | 不能捕捉（已读不回=默拒、拒信，都在平台内部） | 用户手动更新 + 排提醒；可设"逾期未回=视为放弃/再跟进" | 用户 + 应用提醒 |

**只有「已投递」能由应用确证（且仅在内置浏览器路径）；「已通过/已拒绝」只能靠用户配合 + 应用排跟进提醒。** 平台生死（liveness）程序能读，但"通过/拒绝"是平台不给第三方的私密态——没人能自动化读到。

## 11. 规模、方向与市场信号（2026-08-19 grill 定稿）

> §1~§10 把「岗位聚合」做成了能跑的地基，但卡在一个尖锐事实上：**每平台 5 条、三平台一轮，量太小**。岗位聚合"能用，但不好用"——用户不如直接上平台投。这一节 grill 收敛出**规模怎么扩、方向怎么立、市场信号怎么出、追踪怎么收**四大块，把投递从"演示"推向"真能用"。

### 11.1 规模是根

- **要的是量，不是时间深度**：几百~一千份是"投递功能真能用"的基础值（求职常识量级）。窄市场挖到几百份，自然落到几个月前的岗——那是**结果不是目标**。
- **慢的根因 = 限流 + 逐条开详情干等**（job51 详情 JD settle 5.5s，见 §7.8），不是"抓不到"。拿量必须靠**后台限速爬**扛。
- **限速 ≠ 绑人速**：后台爬虫请求间 `sleep + 随机抖动`（不像机器人），常驻运行，吞吐与人操作解耦。**2026-08-31 已废手动「立即刷新」**——岗位只来自事件驱动的后台爬（见 §8）。
- **触发 = 总开关「开启求职之路」**（2026-08-31 定稿：废手动按钮 + 废 15min 轮巡，改事件驱动）：投递页顶一个总开关 + 确认弹窗（"方向定好了吗？"）。**钥匙交给用户**——做简历时还没想好，不该半推半就投。点了才启动后台爬；方向为空则引导"先去定方向"（对方向硬门控、对完善度软确认，由人判断）。触发条件 = 未处理 ≤ 触发值，前端处理岗位后 `kickCrawl`（§8 完整规格）。
- **批量 = 一个循环，无阶段**（2026-08-31 §8 修订）：每轮同一个操作（游标起、扫 cap 页、凑 quota 停、去重、推进游标），空页→exhausted 当天跳过转天回第 1 页、撞 cap→游标回第 1 页。「深爬 → 稳态」是同一循环的自然现象（库里空看着像攒量、绕满一圈去重滤掉老岗看着像盯新），**不是阶段机、无过渡事件**。每平台 quota/cap = 设置项（§8）。
- **消费触发（批节拍，天然限速）**：处理岗位 → 未处理 ≤ 触发值 → `kickCrawl` 爬下一批。**两批之间的间隔 = 人处理岗位的速度（人速）**——平台看到的是"隔很久才来一次、一次拿一批"，不像机器人。触发值 / quota / cap = 设置项。**三层开关（别混）**：`apply_mode` 大闸（on/off，重启读）> 消费触发（未处理 ≤ 触发值）> 在场即踢（进投递页受闸踢一次）。

### 11.1bis 回看节拍：~100 岗 + fail-fast

**决策：数据量达 ~100 岗左右回看一次市场信号（count 阈值、节点触发，不实时 push，与方向面板看门人一致）。** 但补一条 fail-fast：爬出来**几乎为 0** 要立刻报（方向可能错了），别等攒到 100。定位摆正——100 岗回看 = **早纠错**（发现方向完全不对），不是**下精确结论**（样本偏小，薪资分布/技能频率会抖）。

### 11.2 方向 = 派生事实（存 user_facts，非独立配置表）

**决策：投递与简历之间缺一个「方向」，它是桥梁，建在数据层、不在 graph 层。** 共享视野靠**共享真相源**，不靠共享执行流——简历/抓取/市场三块跑在完全不同的触发器上（聊天驱动 / 定时 / 周期），焊成一张大 graph 是触发器错配 + 架空"人拍板"。

**方向 = 派生事实，存 `user_facts`**（2026-08-19 后半段修正，推翻"独立配置表"）：方向是"从聊天内容抽取总结"出来的，改方向 = 聊出新目标 → 新 fact supersede 旧 fact——正是 `user_facts` 的追加+溯源本职（`status` active/superseded），不违反 facts 语义。**不是独立表**——一份源（facts）两个下游（简历 / 抓取），靠**派生**不靠复制。

- **两个不同的东西拆开**：「求职目标」（"我想找前端、期望上海"）是一条 **fact**（`record_facts` 记，source=chat）；「搜索词」（"搜 ['前端','web前端','vue']"）是从目标**派生**的翻译，由提炼服务产出。
- **搜索词 = 查询组 + 多查询（2026-08-21 二维化）**：搜索词为**二维查询组 `list[list[str]]`**：**组内多词**（组内词空格 join 成一条 query）、**组间 OR**（多组各查一遍，结果靠 `external_id` 同源 upsert 去重，不依赖平台）。**多查询是手动展开**，且 **lazy**——凑满批大小就停，后序组只在前面组抓干后轮上。
  > **2026-09-11 实测修正**：原表述「框内空格分词 = AND」**被证伪**。平台对多词是**自适应 AND**——有交集时按 AND 算，**交集不足时静默放宽成 OR**（返回只满足一个词的结果），且放宽时留哪个词与词序无关、不可控。另：平台**自带变体匹配**（搜 `vue` 覆盖 vue2/vue3/vue.js），列同义变体是白费功。写法改为「一组 = 一个概念 + 一个与它**大范围共现**的收窄词，同义变体只留最强的一个，2~3 组起步」——详见 `app/skills/direction/SKILL.md` 与 。
- **role 与 keywords 是两份独立数据（2026-08-21 收尾）**：`role`（目标岗位标签）给简历生成（target_role）+ 方向展示用，**不参与搜索**；`keywords`（查询组）只管搜索。两者内容可重复但**互不派生、不混用**——一个 role 可配多套 keywords，且 role 不只被"方向"这一个逻辑消费（简历生成也用它）。

**v1 一次一方向**（砍掉 weight/软标记/转行试探/广度探测 → 线头）。方向（fact）的不可约字段：

| 字段 | 说明 |
|---|---|
| `target_role`（fact 的 title） | 目标岗位的人话标签（"全栈工程师"）——**独立字段**（简历 target + 面板显示；**不参与搜索**，可被多套 keywords 复用） |
| `cities`（存 direction fact 的 points） | **城市，与 `keywords` 平行等长**（2026-09-13）——每个查询组配一个城市，`["Java","后端"]` 配成都、`["产品"]` 配杭州各搜各的。**逐组必填**，无「全国」（前程无忧留空=回落 IP 城市，语义是坏的）；落定前 `len(cities)==len(keywords)` + 逐项 25 城白名单**双校验出声**。方向**无**单值城市字段 |
| `keywords`（存 fact 的 points） | **二维查询组**（`[["Vue","前端"], ["前端开发"]]`）——组内多词（自适应 AND）、组间 OR；落盘 points = `[" ".join(g) for g in keywords]`（组内空格 join）；**与 role 互不派生** |
| `skill_tags`（派生） | 技能标签（喂简历侧重，如 vue/react/ts）——**住 preferences，不重复存** |
| `status` | active / superseded（改方向 = 新 fact supersede 旧） |
| `derived_from` | 溯源（从哪版 facts 提炼） |

**keywords 与 skill_tags 拆开**：下游不同（一个喂抓取、一个喂简历），语义不同。`skill_tags` 归 `preferences`（"突出 X 而非 Y"），`role` 独立字段（写简历/展示用，不参与搜索）、`keywords` 查询组（只管搜索）——**同一份数据只放一处，不跨线复制**。`keywords` 是唯一真·新数据（搜索策略，不是观察不是偏好）。

**方向提炼 = 一次性生成 + 事后编辑**：拉 active facts → 一次 LLM 提炼 → 方向 → 人定稿。**做成 agent 工具 `refine_direction`（产提案暂存）+ `commit_direction`（拍板才写），照抄 `propose_suggestion`/`decide_suggestion` 那一对**（2026-08-19 后半段修正，推翻"非 agent 工具"）。一条 service 真源 `refine_direction(facts)`，三个触发器共用：投递页按钮（`POST /direction/refine`）、对话 agent（首次定方向，聊天里自然聊出目标顺手提炼）、未来复盘 agent（绑同一个 tool）。

**改方向 = 人拍板（2026-08-25 口头化）**：agent 只负责敲定「方向改成什么」，岗位处置由后端卡门 + 前端就地弹窗，两者拆分。工具产提案**不自动写 facts**——方向是决策（人拍板），keywords 是 LLM 的发明，拍板才 commit。

### 11.2bis 改方向 = 面板可编辑 + 聊天内口头确认（2026-08-25 口头化，推翻旧「卡片 + 两次确认」）

**旧版「聊天内方向提案卡 + is_new_direction 两次确认」已推翻。** 方向是单值决策（不是优化点那种一堆要逐条追踪的建议），卡片 + 内存单例是过度设计；岗位处置判定从「颠覆 vs 微调」简化为「有没有未处理岗位」。新形态：

1. **方向面板可编辑**（投递页，出口一）：岗位标签（role，写简历/展示用，不参与搜索）+ 查询组 `QueryGroupsEditor` 增删（组内 `TagsInput` 多词 = AND、组间 OR）+ **每个查询组一个城市选择器**（2026-09-13——城市挂在组上，不再有方向级单值城市；逐组必填）。role 与 keywords 独立编辑、互不派生。
2. **聊天内口头化**（出口二，与优化点同构）：agent 走 `refine_direction` 工具提炼方向（只读不落库）→ 口头转述 + 问用户认不认 → 用户口头拍板 → `commit_direction` 落库。**无卡片、无暂存单例、无 direction_proposal 透传**。
3. **commit 只写方向，返回 `pending_disposal_count`**（落定后仍未处理的岗位数）。两条通道（agent 工具 / 投递面板保存）都走同一套 commit 语义。
4. **岗位处置 = 后端卡门 + 前端就地弹窗**：`pending_disposal_count > 0` → 就地弹「有 N 个未处理岗位，随新方向保留还是清掉？」——留 = 什么都不做；清 = `POST /direction/dispose-unprocessed`。**与 agent 无关**：agent 不管岗位，后端检测、前端弹窗，在哪改的在哪弹。

**改完方向通知 agent**：方向存 facts（`目标岗位：X` / `目标城市：X`），对话 agent 每轮注入 active facts（`chat_tools.build_deep_system_prompt`）——方向一变，agent 下一轮自动知道，无需额外通知通道。另补一条 event 气泡（按钮路径）让动作在聊天历史里可见。

### 11.2ter 改方向的级联（按投入分层）

**连续性分叉（`is_new_direction` 微调/颠覆）已砍（2026-08-25）**：岗位处置不再区分「颠覆 vs 微调」，统一「有未处理岗位就弹」。微调换关键词多弹一次窗、点个「留」，比 LLM 判错漏弹更可接受；「归档可逆」仍为 v1 线头（微调不归档 / 颠覆归档的差异留到多方向时再实现）。

**投入分层**（改方向时岗位怎么处置，按"投入程度"分，不铁板一块）：

| 层 | 现有表达（`job_followup_events`） | 改方向时 |
|---|---|---|
| 未处理 | 无事件记录 | **只对这批决策** |
| 不再追踪·主动放弃 | `not_pursuing` + reason=withdrawn | 无条件保留（你的判断，不随方向变） |
| 已投 / 追踪中 | 有 `applied`/`interviewing`/`offered` 事件 | 无条件保留（进追踪沙漏，面试不因换方向消失） |
| 不再追踪·其它 | `not_pursuing` + reason=failed/job_closed/duplicate | 无条件保留（你的反馈资产） |

**只有"未处理"那批跟方向绑定**，改方向时两条路：**留着**（什么都不做）或 **删掉**（`dispose-unprocessed`）。**不做"先处理完再切"**——岗位池靠后台爬很快能攒回，不稀缺；画蛇添足。可逆性（归档）才是真正防"颠覆"的底气：试新方向零风险，旧的随时切回（v1 线头）。

### 11.3 市场信号（2026-08-31 砍，被 query_market 取代）

> 本节的「机会集」方案（从 jobs 聚合 `total/by_city/by_source`、摆方向面板）**从未实现，且 2026-08-31 砍掉**——判断「方向对不对 / 你 vs 市场缺什么」由简历 agent 的 `query_market` 工具现场查猎聘承担：现场查、即查即弃、只吐原始统计、判断在 agent 那张嘴。落库画像 + 独立分析管线是过度设计。市场调研唯一保留的长线线头 = **低频广度探测**（见下）。

- **市场信号 ≠ 全市场格局**：深度爬来的 jobs 是"搜了你的方向才进来的"，是**有偏样本**。算不出"全栈 vs 前端谁在涨"——全栈岗压根没机会进库。拿回声当市场声音是自欺。（query_market 也一样：仅猎聘样本、诚实标注，不装全市场。）
- **回答不了的**：要不要转行、哪个方向在涨——那需要**低频广度探测**（市场基线采样，跨几十角色各抓前几页、只喂信号不喂投递），query_market 回答不了这个（它只查你定好的方向），故保留为线头。
- **信号是证据不是决定**：判断永远在 agent + 人拍板，不做自动改方向。

### 11.4 追踪 = 沙漏漏斗

**决策：已投递的后续追踪是"人和 AI 共同做的一件事"，呈漏斗状逐级收窄。** 已投递 → 有回复的收束 → 进面试的收束 → 面试结果好坏再收束。**被拒绝不是没意义，是"没有后续追踪的可能"，但拒绝理由本身有研究价值**（喂市场分析/复盘）。

只有「已投递」能由应用确证（且仅内置浏览器路径）；「已通过/已拒绝」平台不暴露给第三方，靠用户手动回报 + 排跟进提醒（§9）。

### 11.5 四档降级梯子保留（架构，非实现细节）

§7.2 的四档降级梯子（全自动/半自动/手动-观察/手动-外部）是**应对"平台不稳定"这个常态的架构**，不是实现细节，**保留**。"落在哪一档"是运行时探测结果，不是设计阶段要拍板的取舍——投递流程里不纠结"做全自动还是半自动"，答案就是"四档、运行时落位、自动优先、撞墙退手动"。

### 11.6 全生命周期闭环（一页纸）

```
燃料：facts（实力+期望） + jobs（市场）
桥梁：方向（派生事实，存 user_facts，keywords 派生自目标 fact）
节拍：方向面板是唯一"看门人"，节点触发不实时 push

① 定方向   冷启动：做简历时一轮「目标交流」（record_facts 记 target_role）
            → 从 facts 一次性提炼 → 方向 → 人定稿
② 开启求职之路 总开关 + 确认弹窗 → 后台限速爬（catch-up → 稳态），读方向替换硬编码
③ 投递前调整 证据=市场信号（机会集）：市场 vs 简历错位、方向 vs 能力错位 → 提案 → 人拍板
④ 投递     四档降级梯子（运行时落位；自动优先、撞墙退手动）
⑤ 追踪     沙漏：已投递→回复→面试→结果；拒绝理由也采集
⑥ 投递后调整 证据=追踪结果：调简历 + 调方向 → 提案 → 人拍板 → 回到②/①

铁律：AI 出提案，人拍板。没有一步自动改方向；改方向走三道闸（聊→diff→拍板），按连续性分叉+投入分层归档。
```

**调整复用同一套面板**：投递前调整 = 拿市场信号喂「简历优化建议面板（§1.2）+ 方向面板」；投递后调整 = 拿追踪结果喂同一对面板。不新造第三、四套 UI。

> **§11.6 是骨架，§11.7 是血肉（2026-09-13 补）**。上面三个方框（③④⑥）此前只写了「证据 → 提案 → 人拍板」，**没回答"证据是什么、提案长什么样、谁送、怎么让用户看见"**——§11.7 把这半补上。另注：③ 的「市场信号（机会集）」已砍（2026-08-31，见 §11.3），③ 的证据改为 **JD 正文**（§11.7）。
>
> **§11.7 的"送达"答案（2026-09-13 定稿）**：**分析不需要被送达——它就在那儿**（投递页顶部可展开的分析控件）。③④⑥ 的"提案 → 人拍板"落成：分析产出「处方」→ 点「改进」收录进「优化点」面板 → **优化点本就注入聊天 agent** → 去简历页拍板改简历/改方向。

### 11.7 投递页分析（2026-09-13 grill 定稿）

> 本节已 grill 到底（31 问），是**落地执行的唯一依据**。核心判断：**分析不是"被送达的消息"，是页面的一部分**——翻到哪个 tab、点开那个控件，就看到那个 tab 的分析。由此消掉了此前所有纠结（pull/push、待定栏会不会烂、谁触发主动分析）。

#### 11.7.1 形态：顶部一行控件，点击展开（**不是右栏**）

投递页**不做左右分栏**。分析收进页面**顶部一行控件**（与"投递时间选择器"同款样式与外观），**点击后展开分析面板**。

- **为什么不是右栏**：固定右栏 = 暗示"分析默认开着、一直要参照"——**显然不是**。多数时候你只瞥一眼列表。收起来更利落。
- **展开面板内容**：一段总览报告 + （未处理 tab）若干条处方建议。

#### 11.7.2 三个 tab，三套分析（**录用 tab 不做**）

| tab | 分析 | 产出物种 |
|---|---|---|
| 未处理 | **适配度 + 改进方向**——本批岗位"你够不够、缺什么" | **处方**（+ 总览报告） |
| 已投递 | **投递日报**——投了什么 / 谁回了 / 谁石沉 / 回的共性 / 没回的共性 / 趋势 / 鼓励 | 嘱咐（纯报告） |
| 面试 | **单场准备**——JD 分析 + 面试 tips（在**单场面试详情弹窗**内，非 tab 级） | 嘱咐（纯报告） |
| 录用 | **不做**——"用户比谁都清楚自己怎么拿到 offer"，硬提"成功经验"是编相关性 | — |

**"没资料就不强行做"**：拿不到就空着或明说，**不硬编**。

#### 11.7.3 两种产出物种：处方 vs 嘱咐

（术语 → CONTEXT.md「处方 vs 嘱咐」）

- **处方** = 可执行、被追踪、有生命周期的建议 → **只由「未处理」分析产出**。落 `optimization_pending`，初始状态 **`proposed`**。
- **嘱咐** = 有参考价值但不被追踪的结论（"投了很久没回音的共性是…"、"面这家可以多准备 X"）→ **已投递、面试**产出。是「分析报告」的一部分，**没有状态、无处收录**。

**医生比喻**：开药 vs 嘱咐多喝水——**开了药你得复诊**（有状态），**嘱咐过就过去了**（随报告）。

#### 11.7.4 两种数据源，两种分析法

一批岗位来自两个平台，**信息类型不同 → 分别处理**：

| 源 | 有什么 | 怎么析 | LLM 调用 |
|---|---|---|---|
| **猎聘** | 结构化（`skills` 标签 / 薪资 / 学历 / 年限），**无 JD** | **代码聚合标签**，最后一次 LLM 出叙事 | ~1 |
| **job51** | **JD 全文**，结构化字段空 | **逐岗读 JD 提炼 → 合并** | ~20（每岗一次） |

一批最多 60 个（猎聘 quota 40 + job51 quota 20，`schemas/settings.py`），实际成本 **~21 次调用**。深度不同 → 分栏标注（"深度分析（有 JD）/ 概览（无 JD）"），别让用户以为覆盖不全都一样深。

#### 11.7.5 触发与缓存

| tab | 何时算 |
|---|---|
| 未处理 | **一轮爬完就算**（展开只读） |
| 已投递 | **进页面时**看报告日期，没有**"截至昨天"**那份就算一份 |
| 面试 | **展开该场次时**算 |

- **算一次存一次**：落库缓存，按各自键（批次 id / 日期 / 面试 id），**不重算**。
- **已投递的日报截至「昨天」、不以今天为窗**——昨天已过去、报告是**日期的纯函数**，故永不需复算（用户定：日报就该是"昨天发生了什么"，不在你上班中间自己更新）。趋势/存量**往回看 N 天**即可，不需要今天。
  - **坑**：代码全用 UTC，而"今天"是**本地日**（UTC+8）——按 UTC 算会把今天投的岗算进昨天。**按本地日算**。
- **展开不算**（未处理是爬完才算）：首次展开若缓存未就绪，显示"分析中…"（人就在面板前等，无需推送）。

**"一轮爬完"的落点（2026-09-14 落地时定）**：
- **一轮 = 一次 kick**（后端猎聘一段 + Electron 前程无忧一段），`round_id` 由 kick 统一分配、两平台共用——批次键必须跨平台（§11.7.4 的批次本就假定"一批来自两个平台"）。
- **触发点在前端 kickCrawl 尾部**（`GET /analysis/unprocessed?round_id=`）——等前程无忧那段跑完（那个慢），后端不耦合爬虫 service。**分析范围 = 本轮进库的那批**（用户定：检索条件会改、轮次间不可比）。
- **端点非阻塞**：有缓存直接返回；没有则起后台任务返回 `computing`，前端轮询到 `ready`。**无岗位的轮次返回 `missing`**（不起任务、不写空报告）。
- **`analysis_reports.content` 只装嘱咐**；`batch` 的**处方**另落 `optimization_pending`（`status=proposed`）——报告与处方是"一屏两物"。

#### 11.7.6 流程形状：**graph 化 + analyze 用 Agent**（2026-09-15 方向修正，经确认）

> **修订说明**：本节原文写「不建 graph、不用 agent、不用工具」（理由：三步纯线性，graph 用不上）。
> 那是**未与用户达成共识即落文档**的表述，2026-09-15 经讨论**作废**。新方向：批次分析 graph 化，
> analyze 用带工具位的 Agent——理由是「**节点即扩展点，将来加复杂编排（查市场/公司情报/人门）
> 直接插节点，不用颠覆重来**」。原「不建 graph」的两个论据（纯线性、agent 击穿缓存）在新设计里
> 这样化解：graph 仍是**线性骨架**（不硬造分支），缓存语义**不变**（`scope+scope_key` 落
> `analysis_reports`，Agent 的非确定性不击穿缓存——产物照样「算一次存一次」）。

骨架（`app/graphs/analysis.py`，线性，节点即扩展点）：

```
route_scope → load(取数) → prepare(备料) → compute_stats(代码前置统计) → analyze(Agent) → persist(落库)
```

- **一个 graph 按 scope 分流**：scope 是 state 字段；**batch（未处理）与 daily（已投递）都已接通**（2026-09-15 一日内先后落地）——同一骨架、按 scope 换取数/统计/分析。interview 数据薄、暂不并入（散在详情弹窗里，无编排需求）。
- **前置动作用代码做**（定稿）：`compute_stats` 用确定性代码算技能词频/城市/薪资/学历/年限分布（`app/services/analysis_stats.py` 的 `compute_stats` → `StatsPack`），零幻觉零成本，既是 analyze 的 prompt 素材、又是配图的数据源。
- **analyze 用 Agent（带工具位，第一版克制）**：`app/agents/analysis.py` 的 `run_batch_analysis_agent`。形态是「进可攻退可守」——本版工具集留空（行为退化为一次结构化调用），但接口留好「挂工具升级 deep」的门；将来要「边分析边查市场/查公司情报」时挂工具即可，节点不动。
- **分层红线守住**：取数/备料/落库由 service **注入**节点（`run_analysis(load_jobs=, prepare_materials=, persist=)`，照 rewrite `generate_json_from_facts` 先例），graph/node 不 import repo、不碰 DB。job51 逐岗 JD 提炼（逐岗 LLM 的重活）留在 service 的 prepare 阶段，不进 graph。
- **判断在 LLM 里（prompt），不硬编关键词表**。与 `query_market` 的分野不变：那是即查即弃的外部快照；本分析是对本地数据的结构化分析。

**自由配图 + 文/图穿插（2026-09-15 定稿）**：报告正文是**有序块流** `blocks: list[ReportBlock]`（`app/schemas/report_block.py` ⇄ `frontend/src/types/report_block.ts`，双侧同构）——analyze Agent 按叙述顺序产出 `text`（Markdown 段）/ `chart`（内嵌 ChartSpec）块，**图插在讲它的那段文字之后**（讲一段→配一张→再讲一段），不再是「正文 + 尾部图集」。图表 **0~4 张**、宁缺勿滥。
- **ChartSpec 契约**（`app/schemas/chart.py` ⇄ `frontend/src/types/chart.ts`，双侧同构）：6 种图型（bar/line/area/donut/pie/radar）、series ≤ 2、`x`/`series.key` 必须在 data 行里真实存在。桑基/热力/漏斗等对数据形状苛刻、模型自由发挥易配废，不开放。
- **数据必须来自 compute_stats 的 StatsPack**（prompt 里只给这份统计，不许编造）。
- **前端校验兜底是红线**：坏块单独丢、text 块照显——store 映射层 `toReportBlocks` 先洗一道（kind 不认得/空 md/chart spec 过 `isChartSpec` 才留），`ChartRenderer` 渲染时再兜一道。模型配错图只少一张图，绝不拖垮整段文字。「让模型自由配图 + 穿插」能上线，靠的就是这道兜底。
- **兼容旧缓存**：content 里没有 `blocks` 只有 `body` 字符串时 → 折成单个 text 块（旧报告照样读）。
- **演进策略**：先让模型自由配（不固化任何图）；跑一阵子看哪类图真趁手、值得固定，再固化到具体位置（那时退化为确定性出图，不再靠模型）。

#### 11.7.7 闭环：点「改进」→ 优化点 → 聊天 agent（**已有机制，不需新建**）

```
分析产出「处方」(optimization_pending, status=proposed)
   ↓ 用户点「改进」
优化点面板 (status=pending)   ← 到这一步，聊天 agent 自动就看见了
   ↓ 去简历页跟 agent 聊
agent 改简历 / 提议改方向（refine_direction / commit_direction，均已存在）
```

- **「改进」= 一次状态转换**：`proposed → pending`。**分析面板与优化点是同一行的两个视图**，不是两份数据、不存在"同步"。
- **Agent 不需要接收动作**：优化点面板**本来就每轮注入**聊天 agent 的 system prompt（`_assembly.py:31` → `render_panel` 四栏）。`proposed` 的行**不注入**——「改进」就是那道帘子。
- **优化点面板需排除 `proposed`**（否则分析建议一产出就"已经在待办里"，「改进」按钮失去意义）。
- **方向降级归聊天 agent**（用户定）：投递页**只做分析**，不产可执行的方向建议。"迎合不了市场 → 换方向"这种判断由 agent 在聊天里做。**投递页不自动化降级。**

#### 11.7.8 要补的洞（都是既有短板，不是新功能）

| 洞 | 现状 | 怎么补 |
|---|---|---|
| **`jd_status`** | `description==""` 分不清"岗位真空"与"抓失败"（`readDetailJd` 失败返空串、照存） | 加列（none/fetched/failed），填在 `electron/services/job-scraper.js` 的 `readDetailJd` 返回处 |
| **`optimization_pending.origin`** | **无来源字段**（全部列见 `app/models/optimization.py:42-56`），分不清 agent 提的还是分析产的 | 加列（`agent` / `job_analysis`），面板渲染带上 |
| **建议被操作，agent 要知道** | **状态可见、动作不可见**：每轮注入能看到四栏，但看不出"你刚动过它"（覆盖式 `UPDATE status`；无 `updated_at`、无事件表，拒因 `reason` 都不落库） | ① 加 `updated_at`（status 变更刷新）；② **接上变化标记**——`render_panel` 的「← 你刚改的」已写好，但原设计的 `initial_panel` 参数**从未被调用方传过**（`build_deep_system_prompt` 每轮现读面板、拿不到"开跑前的对象"）＝死代码。**实现时改为传时间点快照** `changed_since`（`_assembly.begin_turn()` 记开跑时刻，`updated_at > 快照` 即标）。**不建事件表、不加操作人**（单用户） |
| **`crawl_round_id`** | 无批次概念（`is_new` 是会被覆盖的瞬时标记） | 加列，**首触即定**（下面单独说） |

| **拒因 `reason` 不落库** | `/optimization/reject` 收 `reason`（schema 注释"记进偏好"），service 只 `logger.info`，**不落库**；面板还传空串 | 落库 + 补"能力不到"这类值（**线头**：这是方向降级的证据来源，但降级本身归 agent，本波只保证证据不丢） |

> **`crawl_round_id` 与 `found_by_query` 共用同一条铁律：首触即定。** 猎聘路径**每轮都重新抓到旧岗**（`crawl.py:222` 的 `seen` 只是本轮内集合，不从 DB 播种）→ 送 upsert；`upsert_job`（`repositories/jobs.py:146-153`）是逐字段 setattr 全覆盖。**所以这类"来源/归属"字段必须排除在更新之外**（和"不动 `created_at` / 用户反馈"放一起），否则会被后一轮改写 → 归属错乱、重复分析。

## 12. 跟进 = 单一状态线（2026-08-30 grill 定稿）

> §11.4 画了沙漏（已投递→回复→面试→结果），但「几档、各叫什么、可回退、投递动作要不要独立」全没成词。这一节把 ④ 投递执行 + ⑤ 跟进 从「线头」收敛成**一条手动状态线**——v1 手动挡基线，自动化是渐进升级。术语 → `CONTEXT.md`。

### 12.1 两轴拆分：投递动作（砍）vs 后续状态（留）

**「投递动作」和「后续状态」是两件事**：动作 = 这一次投递的成败/败因（成功 / 失败-已投过 / 失败-错误），是 **L2/L3 自动化**（应用驱动投递）才需要记录的——因为那时是应用驱动、要捕获「这次动作到底成没成」。**手动挡里「我投了吗」由人直接标「已投」，没有「这次动作」要记**——投递中途出错就重试、标「已投过」就标已投。故 **`投递动作` 砍掉留线头**（将来 L2/L3 时作为「如何抵达已投」的附加记录回来，成功则顺手写「已投」）。

### 12.2 后续状态 = 一条线性状态线

```
（空着 / 无记录）＝ 未处理 —— 初始态，爬进来还没看
   │
   ├─ 已投递 → 面试 → 录用           （正向，循序推进）
   └─ 不再追踪（+ 原因）             （负向终态，一个态内部分类）
```

- **起点「空着」 = 未处理 = 无记录**——正好是现有 `count_unprocessed_jobs()` / `dispose-unprocessed` 的语义，不动。
- **「没投」不是一个状态**——它就是「空着 = 未处理」。「我看了觉得不合适、没投」= **主动放弃**（`withdrawn`），不新造第三个概念（旧 `job_screening` 的「没投+6 值原因」是把这个想重了）。
- **砍「有回音」**：「回音」本身没信息量，有信息量的是**进到下一步**（电话聊 / 面试邀约）——对方一邀约就从「已投递」推进「面试」，不单开「邀约」态。
- **「面试」是阶段、非原子态**：招聘面试轮次不定，硬切是枚举切太碎的坑（`CONTEXT.md` 已有教训「decision 枚举切太碎」）。附自由文本 `stage`（「技术二面」），update = 改 stage + 追加时间线。

> **2026-08-31 修订**：上面「面试」这一段已被**面试日历重构**取代——「面试阶段」拆 `interviewing`（待面试）/ `interviewed`（已面试，惰性派生态），轮次从 `stage` 自由文本改为**面试场次表 `interviews`**（1:N，每场带 scheduled_at/location/outcome/next_round_id）。详见  与 §12.10。

### 12.3 可回退 + 时间线即真相

- **任意跳、可回退**：状态不是单向漏斗，任意态可回到任意态。真实流程非单调（电话面被拒 → 又捞回来邀约；面完以为被拒 → 隔周录用；offer 又撤销）。**状态线是「当前标签」、无强制状态机**——「已投递 → 面试 → 录用」只是推荐路径，跳了怪的（空着直接「面试中」= 内推直达）合法。状态机校验拦不住真实错误（可回退兜得住），只挡合法路径。
- **时间线即真相**：一张追加事件表 `job_followup_events`，**当前态 = 该岗位最新一条事件**（派生，不建快照列），未处理 = 无事件。可回退时「被拒又捞回」这段历史还在——正是 §11.4「拒绝理由有研究价值」的原料。单用户、几百条岗位，派生开销可忽略；省掉「当前态快照 + 日志」两处真相的红线。

### 12.4 不再追踪（负向终态）内部分类

**负向收敛成一个态 `not_pursuing`，内部分类 `reason`**（不并列成六个状态）：

| 值 | 含义 | 旧 `job_screening` 塌缩自 |
|---|---|---|
| `withdrawn` | 主动放弃（不合适/聊着不合适/能力不到） | mismatch / not_suitable / underqualified |
| `failed` | 未通过（拒信/婉拒/默拒）——**原 `rejected`，2026-08-31 改名** | —（新增，原来没有） |
| `job_closed` | 岗位关闭（岗没了） | closed |
| `duplicate` | 已投过（同一岗已在别处投过） | duplicate_push |

外加 `note` 自由文本兜底具体原因（枚举管「哪种不再追踪」、note 管「具体为什么」，不丢结构化筛选、也不堵住细节）。`wrong_push`（爬虫推错了）的反哺回路没建，v1 先丢。

- **`job_closed` 塌进「不再追踪」**：岗位关闭天然就是「不再追踪」的一种原因（岗没了没得追），不再单开一根客观生死轴；§6bis「用户确认关闭」信号仍在，只是载体从 `job_screening.reason='closed'` 换成 `job_followup_events(reason=job_closed)`。
- **`duplicate` 单独一值**：与 `withdrawn` 是两种复盘信号——「已投过」说明岗位重复、该调爬虫去重；「主动放弃」说明筛的标准变了。塌了以后分不开。

### 12.5 事件表形状（一张追加表）

```
job_followup_events
  id         自增 PK
  job_id     外键 → jobs.id（index）
  status     applied / interviewing / offered / not_pursuing
  reason     withdrawn / failed / job_closed / duplicate（仅 not_pursuing 有值）
  stage      自由文本（仅 interviewing 有值，如"技术二面"）
  note      自由文本（这次变化的"为什么"）
  source     user（v1 恒 user；L2/L3 观察/自动来了记 observer 兜底）
  at        时间戳（= 变成这个状态的时间，跟进 tab 排序键）
```

### 12.6 现有 `job_screening` 作废清空（不迁移）

**决策：清空重来，不迁移**（用户拍板）。旧 `job_screening` 的「已投」是真实历史动作、本值得迁，但 v1 本地单用户、反馈量小，迁移不值（对比 user_facts 嵌套模型那轮「检测旧结构重建表」——那边历史值钱，这边不值）。`job_screening` 整表删除，`job_followup_events` 全新开始，所有岗位回到未处理。

### 12.7 界面 = 状态 tab，每个状态一个独立列表

投递页拆成一排状态 tab，**每个 tab 一个独立列表 + 计数**（漏斗量一眼可见）：

```
未处理(32) | 已投递(15) | 面试(4) | 录用(1) | 不再追踪(28)
```

- **未处理 tab** = 现在的发现列表（鲜活度排序、立即刷新、投递窗口全继承）。
- **已投递 / 面试 / 录用** = 跟进管道，各一张列表。
- **不再追踪** = 一个 tab（不按 4 个原因拆 4 个 tab——「被拒有研究价值」靠原因字段在、能筛能读，不靠独占 tab）；行上带原因 chip + **顶部一个原因筛选下拉**。

**hover 遮罩快推**（把「推一下」压到一次悬停一次点击）：岗位卡片 hover 时蒙一层灰色半透明面板，蒙上层一排按钮：

| tab | 按钮①（正向下一态） | 按钮②（负向终态） | 按钮③（其他） |
|---|---|---|---|
| 已投递 | 面试 | 不再追踪 ▾ | 其他 ▾ |
| 面试 | 录用 | 不再追踪 ▾ | 其他 ▾ |
| 录用 | （无正向）→ 不再追踪 ▾ | 其他 ▾ | — |
| 不再追踪 | （已在此）→ 回到已投递 | 其他 ▾ | — |

- 按钮① = 正向序列的下一步（高频 90% 一键）；按钮② = 负向终态（下拉选原因）；按钮③「其他 ▾」 = 其余任意态（跳级/回退）。
- **终态 tab 只两个按钮**：`录用` 无正向下一态、按钮①换成「不再追踪」（offer 被撤/主动拒）；`不再追踪` 已在此、按钮①换成「回到已投递」（被捞回）。不为整齐硬凑三按钮。

### 12.7bis 未处理 tab = 点卡片直开投递窗口（不弹选项按钮）

**未处理 tab 不套用上面的 hover 选项按钮**——它是「发现」，不是「跟进」，用户还没看过岗位，第一步是**看**、不是**标状态**。

- 卡片 hover → 蒙灰色半透明玻璃，**只显示几个字「点击查看详情」**，不弹选项按钮。
- **点击卡片 → 直接打开内置网页窗口，跳转岗位 URL**。**砍掉中间那个「详情弹窗」**（原来「点卡片弹弹窗 → 再点查看详情才开网页」两段式啰嗦，弹窗没信息量）。
- **一岗一窗，不复用窗口（2026-08-30 定）**：登录态早与窗口解耦（靠 `partition` 持久化到磁盘，与窗口无关，见 §7.7）——「同平台复用窗口」当初是误以为能保登录态才留下的，真相是登录态靠 `session` 持久化，窗口关不关都不丢。故「复用窗口」只剩「少建一次窗口」的微利（几十~一两百 ms），换「关窗 ↔ 标记这一岗」的一一对应，值。**删掉 `apply-window.js` 里「已有窗口就切 URL」的复用逻辑，每次 `new BrowserWindow`。**
- **关闭内置窗口 → 弹标记框（必选，无「跳过」）**，标记「投了 / 没投（为什么）」：
  - **投了** → 追加 `status=applied` 事件。
  - **没投** → 追加 `status=not_pursuing`，原因只给 **3 类**（2026-08-30 定）：
    - `withdrawn` 主动放弃（不合适 / 聊着不合适 / 能力不到）
    - `job_closed` 岗位关闭（岗没了）
    - `duplicate` 已投过（同一岗已在别处投过）
  - **没有「未通过 `failed`」**——「未通过」的前提是「已投过 + 对方没让过」，语义与「还没投」冲突；硬列「未通过」会把未处理岗位凭空跳到已投递链末端、跳过「已投递」这个事实。**「未通过」只出现在已投递之后的推进里**（已投递/面试 tab 往前推到「不再追踪·未通过」）。
- **关窗标记的跨进程链路（2026-08-30 定）**：岗位窗口是主进程创建的，点原生 `X` → 主进程 `win.on('close')` 拦下（`event.preventDefault()`，窗口保持开着当背景）→ 发 IPC `apply:detail-closed`（带 job 标识）给前端主窗口并拉前台 → 前端弹 Mantine 标记框 → 用户选完，前端**并行**做两件事：① `window.desktop.closeJobDetail()` 通知主进程 `win.destroy()` 真正关窗（**用 destroy 不用 close，防重入 close 事件死循环**）；② `PUT /jobs/{id}/followup` 写状态。两调用 fire-and-forget，互不阻塞。**拦截只对岗位详情窗口生效，登录窗口（登录成功自动 `close()`）不拦**——窗口对象上标 `isApplyDetail` 区分。
- 注意：这个「没投」标记框 = 一次性的投递结果标记，**不经过 hover 遮罩的「不再追踪 ▾」按钮**——两者入口不同（关窗口 vs hover），但写的是同一张 `job_followup_events` 表。

### 12.8 排序 = 处理日期 + 日期分组 + 范围筛选

- **未处理 tab** 按 `last_seen_at`（抓取日）排——发现心智，沿用鲜活度。
- **四个跟进 tab（已投递/面试/录用/不再追踪）** 按**处理日期**排——处理日期 = 该岗位**变成当前状态的时间**（= 时间线最新一条事件的 `at`）。例：8/1 投、8/10 面、8/20 被拒 → 在「不再追踪」排 8/20；被捞回面试（8/25）→ 在「面试」排 8/25。
- **正序/倒序可切换**（最近处理在前 / 最久在前）。
- **日期分割线**：列表按处理日期的日历日分组，每天一条分割线（今天 / 昨天 / 具体日期；跨年带年份）。**天粒度**（非月粒度——跟进心智是「今天投了哪些/昨天处理了哪些」，月太粗）。未处理 tab 也套用（按抓取日分组，后台分批爬时正好显示「这批 8/28 抓的」）。**视觉借 beacon `activityList` 已验证的分割线**：`Map` 保序分组 + 三段式分割线（左右渐变线 + 居中文字胶囊），light 化（浅灰渐变 + 面板色胶囊，非 beacon 深色玻璃白字）。
- **日期范围筛选**：起止日期选择器，只看处理日期（未处理 = 抓取日期）落在范围内的岗位；与不再追踪 tab 顶部的原因下拉**叠加**（先范围、再原因）。**作用域 per-tab 独立**（与排序一致），切 tab 不互相残留。
- **全 tab 共用一套列表组件**：排序键不同（未处理 = last_seen_at，跟进 = 当前态事件的 at），分组/筛选/方向切换同构。

### 12.9 主动跟进（提醒）砍掉留线头

**决策：v1 不做主动跟进（提醒/待跟进队列），先把手动状态链做扎实**（用户原话：满足 80% 需求）。应用不主动催，追不追由用户。硬约束：本地桌面应用、无云端无 push，应用关着没人能提醒——「待跟进队列」只可能是「下次打开摆到面前」，那半件事留作线头。

### 12.10 面试 = 日历编年 + 场次表（2026-08-31 grill）

「面试」tab 从「岗位列表」重构为**纯日历**。核心：把「面试」这个词拆成两层——**面试阶段**（岗位在流水线的位置，状态线管）与**面试场次**（一次具体约面，`interviews` 表管）。日历读 `interviews` 全表、不过滤任何状态，是场次编年，历史可追溯。

**状态线拆两个值**：
- `interviewing` **待面试**——排面试那一刻写入（真实事件），约定时间未到。
- `interviewed` **已面试**——**惰性派生态**，读时按 `now ≥ scheduled_at` 现算，不写事件（本地单用户、应用关着，到点自动写不成立）。

**面试场次表 `interviews`（1:N，挂 `job_id`）**：

| 字段 | 说明 |
|---|---|
| `job_id` | 外键 → jobs.id（**唯一联查键**，经 job 间接连状态线） |
| `scheduled_at` | 具体时间点，必填（上/下午由它派生） |
| `location` | 自由文本，可空（线上填链接、线下填地址，不区分 mode） |
| `outcome` | 场次结果 5 档 |
| `next_round_id` | 显式链指向下一场（自引用外键，只写一次） |

**outcome 5 档线性生命周期**：

```
待面 scheduled ─► 等结果 awaiting ─► 下一场 next_round ─► …（新行 scheduled）
                         │
                         ├─ 录用 offered
                         └─ 未通过 failed（自动 push 状态线，reason 当场选）
```

| 值 | 中文 | 对岗位状态线 |
|---|---|---|
| `scheduled` | 待面 | 排面试时 push `interviewing` |
| `awaiting` | 等结果 | 不联动 |
| `next_round` | 下一场 | 不联动，触发建下一场（新行 scheduled） |
| `offered` | 录用 | push `offered` |
| `failed` | 未通过 | push `not_pursuing`，reason 当场选（未通过/岗位关闭/主动放弃） |

**关键收敛**：
- **「默拒」不是状态**——投了没回音 = 停「已投递」，面了说等消息 = 停「等结果」。没有终局信号就不造新状态。
- **无「取消」档**——没面成要么改期（改时间），要么自然死 = 未通过。
- **结果可回退（任意态→任意态），只做正向联动**——改 outcome 只改这一行，回退时状态线手动退，不自动同步。
- **`rejected`（被拒）→ `failed`（未通过）**：值、中文文案一起改，统一到最委婉的词（避免「被拒」对求职者心态的挫败）。
- **联查键只有 `job_id`**——不指向某条 interviewing 事件（那是派生的、无稳定身份证）。

**日历（自绘月历，参照 beacon `activityCalendar`）**：
- 大格子、格内直放场次条目、按上/下午分区；未来亮标、过去灰底 + 半透明蒙版可点回看。
- hover 遮罩左「详情」右「结果」+「改期」（新时间不早于今天）。
- 详情弹窗：时间/地点 + JD（联查 `jobs.description`）+ 岗位信息；**JD 解析 / 面试策略 / 公司信息 = 线头**（占位「待实现」）。

**入口与 tab**：
- 排第一场 = 改「已投递」tab 的「面试」hover 按钮：直接标 → 弹排面试表单。
- 排下一场 = 场次详情弹窗「安排下一场」。
- tab 结构 `未处理 | 已投递 | 面试(日历) | 录用 | 不再追踪`；「面试」tab 徽标 = 待面试场次数。

### 12.11 信息架构重构：二级导航 + 后端按 tab 查询（2026-08-31 grill）

> 上一版把 5 个状态用 Mantine `Tabs` 顶部横排区分（互斥视图），但项目设计语言（设置页 `settings-nav`）是**左侧二级导航**。这一节收敛：① 视觉换成左侧二级导航；② 顺带把数据流从「一次全拉 + 客户端分组」重构为「后端按 tab 查询」（用上后端早已备好却未接电的 `status/reason/followup` 参数）；③ 补 §12.8 的日期分割线 + 日期范围筛选（原为线头）。

**① 导航形态 = 左侧二级导航 + 视图切换（互斥，非锚点滚动）**。设置页的 `settings-nav` 是「锚点滚动」（分组共存一页、滚过去），但投递 5 状态是**互斥视图**（一次只看一个列表，流水线漏斗）。故只借设置页的**竖向导航视觉**（`.settings-nav-item` 风格 `<button>`），交互仍是**点导航 → 右侧只显示该状态视图**。导航列顶部带「投递」标题 + 副标题。

**② `tab` 不进 URL 子路由（保持内存态）**。`tab` 唯一真相在 `applyStore`（模块级单例，切 section 不丢态），导航项是 `<button>` 调 `setTab`。理由：本地单用户桌面应用，无深链/后退/分享需求；子路由会制造 URL↔store 双真相源 + 非法 tab 回退（`StatusTab` 是派生枚举）。`applyStore` 单例已保证切 section 不丢态，唯一损失是「全量重载回未处理」，对求职工具是合理默认。**将来出现「从别处深链进某状态」需求（如聊天 agent 说"看刚拿的 offer"）再升级子路由**，YAGNI。

**③ 顶栏 chrome 下放 = 「获取侧」与「跟进侧」分离**。检索控制台胶囊（方向/查询组/城市/总开关）**下放到「未处理」视图**——它们只服务「岗位从哪来」；已投递/面试/录用/不再追踪面对「已经进来的岗位怎么处置」，与方向/开关无关。**刷新按钮已删除（2026-08-31 §8⑤）**——严格门控、无「无视 backlog 强行抓」的逃生舱，岗位只来自事件驱动的后台爬。全局顶栏不再有刷新/控制台。**2026-09-01 整合（见变更记录）**：求职之路指示器并入检索控制台胶囊，成为唯一入口（仅未处理 tab）；入口左、排序+日期右同行。

**④ 各视图控件集（2026-09-08 收敛：砍排序维度、统一控件）**：

| 视图 | 语义时间键（排序+范围筛选同键） | 专属控件 |
|---|---|---|
| 未处理 | **收录时间**（`last_seen_at`） | 统一控件 |
| 已投递 | **投递时间**（最新 applied 事件 at） | 统一控件 |
| 面试 | —（纯日历，无排序控件） | 月历 |
| 录用 | **录用时间**（最新 offered 事件 at） | 统一控件 |
| 不再追踪 | **处理时间**（最新 not_pursuing 事件 at） | 统一控件 + 原因筛选 |

- **砍排序维度**：不再有鲜活度/时间/相关度分段器，全 tab 只留「时间」一个维度，每 tab 一个语义时间键。相关度本是死维度（前端不传 query，退化成鲜活度），随此次一并下线；真正的相关度（从简历+事实库提炼关键词）是线头，日后作为新排序维度回归。
- **统一控件（前端样式统一，解决"有的一个、有的两三个"的形态分裂）**：一条横排 = `[语义时间文字标签] [时间范围筛选器] [正倒序箭头切换]`，四列表 tab 复用同一组件、只换前缀标签词。标签前置化解「时间」一词超载——用户能看清此刻按哪种时间排/筛。
- **范围筛选器固定宽度**：足以容纳完整「起 – 止」区间，不随内容（占位词 vs 已选范围）伸缩，避免选前选后整条控件跳动。
- 日期范围 + 正倒序均 **per-tab 独立记住**（`rangeByTab`/`orderByTab`），切 tab 自动套用该 tab 上次的值，不互相污染。**平台筛选已删（2026-09-01）**——未处理 tab 不再有平台下拉（见变更记录）。

**⑤ 数据流 = 后端按 tab 查询**。切 tab **每次请求** `GET /jobs?status&sort&order&reason&start&end`（本地回环几 ms、数据新鲜，无缓存失效复杂度）。排序在后端（`score()` 早已实现四档，前端不再复刻）。响应带 **counts**（单请求列表 + 全徽标）：`{ jobs:[...], counts:{ unprocessed, applied, interviewing, offered, not_pursuing } }`。**`counts.interviewing` = 待面试场次数**（非岗位数，与 §12.10「面试 tab 徽标 = 待面试场次数」一致；语义混已知、接受——它是徽标数不是列表行数）。

**⑥ 后端契约新增**：`GET /jobs` 加 `start`/`end` 参数（闭区间 `[start, end]`，未处理按 `last_seen_at`、其余按 `followup_at` 过滤）；`GET /interviews` 响应**内嵌 `job` 摘要**（`company`/`title`/`description`）——日历自给自足，废掉前端 `jobById` 对全量 jobs 的依赖（日历是场次编年、不过滤状态，靠全量 jobs 联查会漏已面岗位信息）。

> 已砍（2026-08-31，防后人再提）：

> - **用户动作沉淀成 fact**——投递页已有更具体的设计（状态时间线），这条旧线头过时。
