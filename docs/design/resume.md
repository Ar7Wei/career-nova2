# 简历分区 · 设计决策

> **简历分区**的设计文档。记这个分区**做了什么决策、做了什么设计、为什么这么设计**。
> 这里记细节与来龙去脉。术语定义见根目录 CONTEXT.md。

简历模块三大分支：**识别（1.1）/ 优化（1.2）/ 对话式生成（1.3）**，共享同一个**用户信息事实库**。

1.2/1.3 共享同一套**会话模型 + 对话 agent**（见 §11、§12），区别只在姿态与产出：优化 = 对话建议 + 文档任务增量改写；生成 = 对话收齐事实 + 文档任务整份组合。

## 1. 整体架构：文档为成品，事实为唯一真相源

> 2026-08-05 大重构：从「上传→抽取→确认卡片→入库」改为「上传→文档 v1（无 LLM）+ 后台抽取」。

**决策：上传的简历不抽取。MarkItDown 转成 Markdown 就是成品 v1（文档），LLM 从上传关键路径上完全消失。**

旧架构的慢，本质是"上传 → LLM 抽取（60s+）→ 确认卡片 → 入库"这个**严格串行**流程：LLM 在关键路径上，用户上传后必须等识别完才能继续。新架构删掉这个串行：

```
上传简历 ──markitdown（本地、快）──▶ 文档 v1（立即返回，左栏直接看）
                                          │
                             后台任务（异步，不阻塞聊天）
                                          ▼
                             单次抽取 ──▶ 事实入库（source=resume_upload）
```

**三个存储，各司其职：**

| 存储 | 是什么 | 谁写 |
|---|---|---|
| `user_facts`（SQLite） | **唯一事实源**：关于用户的语义知识 | ① 上传抽取（后台，单次）→ 确认后入库 ② 对话挖掘 ③ 手填。每条带**来源 + 时间线**，入库前统一跑冲突检测 |
| `resume_documents`（新表） | 版本化文档，三列并存：`markdown`（上传 v1 抽取物 + 元件兜底）+ `resume_json`（生成版结构化真身，2026-08-28 加）+ `html`（生成版渲染快照，固定模板确定性产出） | LLM 从事实库取材组合出结构化 resume JSON；Jinja2 固定模板把它确定性渲染成 HTML。v1 是上传转出（仅 markdown） |
| `resume_snapshots`（新表） | 事实库整表快照，与文档版本同代 | 每次生成/回滚**前**给"将被替换的当前版本"打一份——v1 上传时无前任、不打，v1 的快照在 v2 创建时才打（§9） |

**文档是成品，不是事实真相源**：文档承载"排版 + 措辞 + 组装后的事实"，是事实的一次投影。源数据在事实库。LLM 生成/修改文档时**只从事实库取材、不编造新事实**——所以文档"生不出"事实库不知道的内容，两份存储天然不冲突。

**为什么 Markdown 是上传 v1 的好载体（2026-08-28 排版转向前的内容层载体）**：
- **层级天然在**：标题结构就是"工作经历条目 → 子要点"、"技能 → 分类子项"——旧架构把每段经历拆成分散的 4 个点、丢失归属的问题（用户痛点 2c/d/e），结构性地消失。
- **文字编排的真相源**：上传 v1 的 MarkItDown 提取物、元件兜底预览都在这一层。
- **生成版的内容层已不是 Markdown（2026-08-28）**：生成产出改为**结构化 resume JSON**（JSON-Resume 词表 + `layout` 映射表），由固定模板（Jinja2）确定性渲染 HTML。Markdown 退居「上传 v1 的抽取输入 + 元件兜底预览」。详见 §13.3。
- **Markdown 不大不长**：一份简历几千字，LLM 整份读入无压力（对话上下文注入用内容层，紧凑）。

**一句话架构原则：能写进简历的 → 文档；对用户的理解/候选素材 → 事实库。两者靠"来源 + 时间线"对账，不靠状态机硬约束。**

## 2. 生成简历的触发权

**决策：双通道（C）**——agent 自主提议（信息够了主动问"要生成吗"）+ 用户显式要求（"帮我生成/改一版"）。触发权不完全在 agent 也不完全在用户，最灵活，符合"一个 agent 灵活跳"。

**生成页数**：默认一页。生成前一步跟用户确认——资料少则一页，资料实在太多则确认一页还是两页。**不硬锁一页**（资深/学术可两页），且页数也是用户可自定义的标准之一。

## 3. 状态机的边界（为什么"灵活跳"不是"禁用状态机"）

**决策：状态机用来约束"数据的状态"是对的；用来锁死"对话的走向"是要避开的。**

- 管**对话流程**（先问啥后问啥）→ 写死就僵。用户可能上来甩一份简历，也可能先聊两句；让他按固定顺序走是灾难。这里必须"灵活跳"。
- 管**数据/事实的生命周期**（`active → superseded`）→ 离散、明确、该被约束，用状态机（status 字段的合法迁移）反而清晰防错。

所以"缺口感知"是**建议** agent 往哪问（提示"技能这块还空着"），**不是强制**——决定权在 agent。

## 4. 用户信息事实库（user_facts）

**定位**：存"对用户的了解"的**原料**——自然语言事实 + 基本分类，全局共享（简历/优化/生成/市场调研都取材）。**是原料不是成品**，整理渲染成简历是下游 agent 的活。

**基本分类（粗归类，非硬 schema）**：基本信息 / 教育经历 / 工作经历 / **项目经历**（2026-08-29 单列，见下）/ 个人技能（含证书）/ 其他补充。工作与技能有交集但侧重不同："用什么干了什么" vs "能用到什么程度"。

**表结构**：`id / category / title / points / source / status / on_resume / occurred_at / created_at / updated_at`
- `category`：basic/education/work/projects/skill/other
- `source`：resume_upload（上传识别）/ chat（对话记录）/ manual（信息库手填）
- `status`：active / superseded（真伪冲突留 history——旧的标 superseded 不删，新的 active）
- **`on_resume`（2026-09-06）**：布尔，该 active 事实该不该渲染进简历成品。默认 True；方向槽位（目标岗位/城市）、敏感隐私、gap 弱点等置 False——只取 `active 且 on_resume=True` 的过滤口径由机器门/生成共享。LLM 在记录/抽取时默认判一次，人可在信息库页开关否决；落库固定、不每次重判。
- **`title` + `points`（2026-08-07 重构）**：**嵌套模型**——`title`（总条目/单句）+ `points`（子要点数组，JSON 文本列，可空 `[]` = 单句事实）。**层级在一条内**，不再用 `group_id` 外键/负索引（负索引依赖 LLM 数数，一偏就丢子条目——用户痛点"看不到子条目"的根因）。抽取器抽"每段经历一个条目带 points 数组"；对话挖掘同理。
- **`occurred_at`**：事实发生的时间线（如 "2018-2021"），是**时间上的来源**——配合 source（地理/渠道来源）做完整溯源，回滚/对账时顺着摸回去。

**写入时机（按批量分）**：
- **后台抽取（上传时）**：上传返回后后台任务**单次抽取**（2026-08-08 起；有确认兜底 + 「重新抽取」按钮，不再多抽对比烧 Token），结果进**前端左栏「抽取信息卡片」**（可编辑，总分两段式，暂不入库）。**卡片确认后才入库**（source=resume_upload）；拒绝则该批不入库、通道重开可重传（见 §6）。**健壮性**：后台任务 try/except 兜底——LLM 异常/空结果 → 状态 `failed` 给可读错误（不静默卡 `extracting`），卡片可「重新抽取」。
- **对话零星记录（单条）**：自动触发，对话框小字提示"记了什么 + 收进信息库"。
- **手填**：信息库界面。

**统一冲突检测（入库前，三条路径贯穿）**：任何事实入库前先做检测——同分类 + 高相似（归一化相等 / 编辑距离超阈值）判定。**比较单元 = `title`**（points 随条继承 title 的判定）：
- **同一实体 + 内容不同**（真伪冲突，如"雅思 7.5"vs"4.5"）→ 新的 active、旧的 superseded 留 history。
- **内容相同/近似**（幂等）→ 不重复写，跳过。
- **不同实体** → 直接写。
重冲突（时间交集等语义矛盾）不预设是错，留给对话澄清。检测在**入库时**统一做（确认入库 / 对话挖掘 / 手填），不在抽取阶段（候选不入库）。

**冲突处理**：真伪冲突（雅思 7.5→4.5）系统点出让用户裁决，新的 active、旧的 superseded 留 history；时间交集矛盾（在读期间工作）不预设是错，先澄清（"是兼职吗？"）。

**收录判定（对话流）**：相关性（跟求职/职业形象有关吗）→ 价值（稳定事实还是闲聊）。"买煎饼果子"不收，"每天提前半小时到岗"收。由 agent 判，不硬编码。

## 4bis. 抽取结构：总分两段式

**决策：抽取用「总（entry）+ 分（child）」两段式，而不是平铺或压缩。** 工作/教育/项目/技能这类「多段并列」内容都走这个结构。

```
A（工作经历，entry）──┬─ A1 子要点
                        ├─ A2 子要点
                        └─ A3 子要点
```

- **A 是「总」**：公司 + 岗位 + 时间段，一句话概括这段经历。
- **A1-A4 是「分」**：A 的每条描述，**忠实逐条搬**，不做压缩。
- **结构语义**：嵌套模型——`title`=A，`points`=[A1..A4]，一条内表达层级（见 §4）。

**为什么不是二选一**：
- **平铺（A1/A2/A3 各自独立）** → 丢结构（归属 A 丢失，一段经历散成 N 点，用户痛点 2c/d/e）。
- **压缩（A 一条）** → 丢细节（多条描述被合并，违背「忠实搬运」原则）。

**总分结构保内容结构性 + 完整性**——与文档天然对齐（Markdown `## 工作经历` 下 `### A 公司` 下 `- A1`），层级不丢、细节不缩。

## 5. 判定标准：硬判只做基础信息，语义项全交 LLM，用户可覆盖

**决策：判断"简历素材够不够好"，硬判只做基础信息，其余全交 LLM，且标准可被用户覆盖。**

调研了市面权威"好简历"标准（Harvard/Google 前 HR Laszlo Bock/Jobscan ATS/Ladders 眼动研究 + 中文大厂 HR 共识），核心高度收敛：成果导向、量化、强动词、为岗位定制、6~10 秒能扫到重点。这些标准可切两层：

- **硬判（规则/本地比对）**：只做**基础信息**——联系方式/邮箱/学历/时间等客观项。判定方式是**拿本地事实库比对**：上传简历后缺哪项跟已有记录对，没有再问用户；聊天生成时先填一张基础信息表再聊别的。
- **LLM 判（语义理解）**：量化、用词、板块结构、卖点/Spike、岗位相关性、个人贡献、竞争力定位——**全交 LLM**。

**为什么不把量化率/关键词命中做成硬判？**（关键否决，防回退）
这是"以全为好"的思维，已被用户明确否决：
- 有人就是没有工作经历（在校生），有人就是没有技术技能（销售）——"写全"对他们不成立，硬判"缺工作经历"是错的。
- **量化本身带欺骗性**：销售业绩可量化，后端开发的成就怎么量化？"人际关系提升 80%"毫无意义。所以量化交 LLM 判断该不该、怎么解读。
- 用词、板块结构同理，是语义活。

**用户自定义标准**：判定标准 = **权威默认 − 用户拒绝项 + 用户自定义**。用户可注入自己的"完美简历标杆/标准"，也可说"我不认这条"。

**偏好（preference）独立表**：用户的判定意志（拒绝项 + 自定义标准）与事实素材分开存。**偏好同事实生命周期**——聊出来 → 确认 → 持久化 → 设置页可编辑（信息库页并列的入口）。

## 6. 抽取信息卡片（后台抽取的确认入口）

> 2026-08-05 重构曾取消确认卡片；2026-08-06 定稿为**「后台抽取 + 左栏轻形态卡片」**回归——保留重构的「上传不阻塞、后台异步、多抽对比」，但加回「抽取结果可编辑、确认才入库、拒绝可重传」的关口。

**为什么回归**：重构让上传不再阻塞，但抽取结果「直接入库 + 对话对账」让用户失去对抽取的一次性把关。用户明确要求——抽取结果应可在入库前**编辑、确认或拒绝**。

**流程**（含上传顺序订正）：
```
上传 → 文档 v1 显示 + [蒙版+进度条]罩住（覆盖 HTTP + 抽取全程）
  → 抽取成功 → 蒙版不消失，左栏弹「抽取信息卡片」（可编辑，总分两段式）
      确认 → 卡片事实统一冲突检测后入库（source=resume_upload）→ 通道关闭（ready）→ 蒙版消失
      拒绝 → 卡片事实不入库 → 通道重开（可重传）
  → 抽取失败 → 蒙版不消失，通道重开（可重传），错误提示 + 文档 v1 仍可看
```

**关键语义**：
- **候选不入库**：抽取结果先落前端卡片（可编辑），**确认后才入库**。未被确认的候选不落库、不留 superseded 痕迹（还没发生）。
- **确认=入库关口**：确认时统一跑冲突检测（见 §4「统一冲突检测」），真伪→superseded、相同→跳过。关闭上传通道（ready）。
- **拒绝=该批不入库**，通道重开（可重传）。
- **卡片可编辑**（非只读）：改 title、删条目/要点、新增条目/要点、调分类，确认后整批入库保留嵌套层级（title+points 一并）。
- **总分两段式呈现**：总条目在前、子要点缩进归其下（见 §4bis）。

**与重构前确认卡片的区别**：① 上传不阻塞——抽取后台跑，卡片在左栏弹、不打断聊天；② 有文档做底——卡片和文档 v1 并排，所见即所抽；③ **单次抽取 + 「重新抽取」按钮**（2026-08-08 起；不再多抽对比——有确认兜底 + 重抽，省 Token）；④ 只读→可编辑、可确认/拒绝。

## 7. 文件提取：MarkItDown 统一编排层

**决策：用 `markitdown` 做统一提取层，把上传文件转成 Markdown。**（本层只转码，理解/抽取在后台 LLM。）

**为什么是它**（备选否决理由，防回退）：
- **自己按扩展名写分派**（pdfplumber/mammoth/charset-normalizer）：底层同一批库，但重复造轮子；格式分派的边界交给 MarkItDown 维护比自己写稳。
- **Apache Tika**：覆盖最全，但要拖一整个 JVM + 后台 Java 服务，本地轻量桌面应用背不动，加重子进程管理负担。
- **LibreOffice headless**：办公格式之王、唯一能靠谱读老 .doc，但要捆绑 150MB+ 办公套件——为低频 .doc 不值；.doc 走"提示用户另存"降级。
- **云转换 API（CloudConvert 等）**：简历是高度敏感信息，本地优先的立身之本是数据不出机；违背"不上云"红线。

MarkItDown 按格式分派到底层专精小库、统一吐 Markdown，内置 charset-normalizer 编码嗅探——与我们"喂 LLM 的就是 Markdown"方向一致，省得自己写分派。我们的入口在调用前**先按扩展名白名单拦截**（`app/utils/extract.py` `_ALLOWED_EXTS`，不收的格式直接 415）；**未启用 magika 按内容识别**（magika 只是 markitdown 的传递依赖，代码未调用）——"改名伪装"不在本地拦截范围。

**输入边界（白名单）**：
- **收**：TXT / MD / PDF / DOCX / HTML / CSV / PPTX / XLSX，装 `markitdown[pdf,docx,pptx,xlsx]`。
- **拒**：音频 / 视频 / Outlook(.msg) / Azure / YouTube / 图片OCR——一律不装对应 extras、入口按扩展名拦截。
- **TXT 乱码**：charset-normalizer 编码嗅探（防 GBK/UTF-8），MarkItDown 内置。
- **扫描件 PDF**（图片型、无文本层）：抽取时检测文本量，抽不出来就弹窗提示"换文本型 PDF 或手打"。1.1 不做本地 OCR（RapidOCR 已砍 2026-08-31，见 §线头）。
- **老 .doc**：提示用户另存 docx/PDF，不捆绑 LibreOffice。

**本地只转码，不动脑子**：本地这层负责"二进制 → Markdown"，理解/抽事实/判断全在后台 LLM。

## 8. 左栏预览分档（C）

**决策：能渲染原件的显示原件，渲染不了的显示解析后的 Markdown 兜底；有渲染层 HTML 的优先显示渲染产物（生成版，2026-08-28 起由固定模板渲染）。**

- **分档优先级（2026-08-13）**：`排版层 html`（生成/改写版，iframe 渲染）> 原件可渲染（PDF/HTML/TXT/MD）> 原件不可渲染（DOCX 等 → Markdown 兜底）> 生成草稿（仅 Markdown）。
- **原件可渲染**：PDF（react-pdf）、HTML（iframe + blob URL 原生渲染，`sandbox` 禁脚本）、TXT/MD（blob 读原文渲染）→ 显示原件。
- **排版层 HTML**（2026-08-13；**2026-08-28 起由固定模板渲染**）：生成/改写版落库 `resume_documents.html`（`render_resume(resume_json, typography)` 确定性产物）→ 前端拉取 → `new Blob([html], {type:'text/html'})` → iframe + `sandbox=""`（与上传 HTML 原件**同一隔离舱机制**：CSS 只作用于舱内不污染应用外壳、禁脚本）。**这就是 §13.3 的渲染产物**——用户看到的生成简历像简历纸，不是 Markdown 文本区。
- **原件不可渲染**：DOCX/PPTX/XLSX/CSV（浏览器/Electron 无原生渲染能力或纯文本直接用 Markdown 等价）→ 显示 **MarkItDown 解析后的 Markdown**。好处是"所见即所抽"，顺便帮用户发现抽取问题。**已实现**：parse 响应带 `markdown` 字段，前端 `ResumePreview` 组件按扩展名分档（PDF→react-pdf / HTML→iframe 原生 / TXT/MD→blob 读原文 / 其余→Markdown 兜底）。

**原件持久化（2026-08-09，修复"重启后 PDF/HTML 变 Markdown"）**：上传的原件此前只活在当次会话的内存 blob URL（zustand 态 + `URL.createObjectURL`），重启即丢、左栏退化 Markdown。现把原件文件落盘到 SQLite 同级 `originals/`（文件名 `v{version}_{消毒后文件名}`，防路径穿越），`resume_documents` 记 `original_name/original_ext` 元数据。重启/回滚后前端调 `GET /documents/original` 拉原件 → `URL.createObjectURL` 重建 blob 原生预览。语义：**原件 = 上传版成品的源素材**——回滚**不产生新文档**（软作废，§9bis），目标稿原件路径不变、**无需复制**；生成版无原件 → Markdown 预览。

**全类型第二次启动原样渲染（2026-08-10）**：PDF/HTML/TXT/MD 四种原生预览格式重启后都走「拉原件 blob → 重建预览」——pdf 走 react-pdf、html 走 iframe、txt/md 用 `fetch(blob).text()` 读原文渲染（当次上传与重启后一致，都显示原文件原文而非 MarkItDown 的 Markdown）。DOCX/PPTX/XLSX/CSV 浏览器渲染不了原件 → 显示后端 Markdown 兜底（内容完整，非"原文"是这类格式的唯一正解）。配套修复：`GET /documents/original` 按扩展名返回正确 `Content-Type`（html→text/html、pdf→application/pdf、txt/md→text/plain|text/markdown——**MIME 错了 blob 无法解析，会卡"正在渲染 HTML"或读不到文本**）；中文文件名用 RFC 5987 百分号编码进 `Content-Disposition`（直接内联中文 → UnicodeEncodeError → 500）。

**HTML 为什么走 iframe 原生而非 Markdown**：HTML 简历的价值在样式布局（内联 CSS、表格、渐变 header），Markdown 兜底会丢全部视觉。用 blob URL 进 iframe（上传时或重启后从原件重建），CSP 的 `frame-src blob:` 已放行、零新增状态。`sandbox` 空属性禁脚本——简历是静态内容，带恶意 `<script>` 也不执行（安全优先）。取舍：HTML 内相对路径资源（`./images/x.png`）在 blob 下加载不到，但简历单文件内联场景可接受。

预览能力与解析能力**解耦**——能解析不等于能看。左栏的"试衣间"是针对**生成的简历**（自产 HTML，必可渲染），与上传原件预览是两回事。

**PDF 预览的 CSP 坑**（Electron 特有，已解决）：Electron 默认禁用内置 PDFium 查看器，`<object>/<iframe>` 渲染不了 → 用 react-pdf（pdf.js 纯 JS 渲染）。pdf.js 走 Web Worker 解析 + fetch blob objectURL，Electron CSP 必须放行：`connect-src` 加 `blob: data:`、新增 `worker-src/child-src 'self' blob:`，否则卡死永不渲染。

## 9. 文档版本化 + 回滚（重构后新增）

**决策：简历文档版本化（v1/v2/…），回滚 = 切版本；事实快照与版本同代，可连事实一起还原。**

**为什么**：封闭通道（简历只传一份，不反复传文件）意味着"改坏 = 丢失"——必须能回滚/重置（用户明确要求）。LLM 偶尔写错、删错、合并错，不能靠用户重新上传一份找回。

> ⚠️ 本节「回滚动作」的机制已演进：旧描述是「纯追加回滚」，**2026-08-10 起实现的是「软作废回滚」**（见 §9bis）。以下 `resume_documents` 版本流、快照机制、事实还原仍是现状，但"回滚怎么改行"以 §9bis 为准。

- `resume_documents` 表：**整张表 = 单用户的唯一简历文档流**（封闭通道，一次只有一份简历）。每行一版（version 递增），v1 = 上传转出（source=upload），vN = LLM 组合产出（source=generated）。
- **回滚 = 软作废**（§9bis）：选定目标稿，其后稿标 `superseded`、目标稿恢复当前，**不删历史**。
- `resume_snapshots` 表：**建新版本前**给「将被替换的当前版本」打一份 user_facts 的 active 行快照（与版本同代，幂等——同版本重打覆盖）。**v1 在 v2 创建时才打**（v1 无前任），天然包含后台抽取结果。回滚时**询问用户**：只回文档，还是连期间收集的事实一起还原（include_facts）。
- **快照语义 = "vN 还是当前文档时的事实库"（vN 任期末）**：vN 快照在 vN+1 创建前打，所以还原 vN = 撤销 vN+1 之后收集的一切。
- **回滚自身也要先给被替换的当前版本打快照**——否则回滚后原当前版本的事实状态就丢了，无法再「回滚回 v3」。
- **回滚目标 = 当前版本时拒绝**（回滚到当下无意义，避免生成重复行）。
- **事实还原**：当前 active 全标 superseded（留历史不删），快照事实重建为 active，**保持嵌套层级**（title+points 一并还原，一条一行无需 id 映射）。**保留来源**：快照里每条事实的 `source` 原样还原（chat/manual 不回退成 resume_upload），溯源不断（2026-08-07 修正）。
- **回到初始版本（V0，2026-08-08 新增）**：版本面板底部「回到初始版本」入口 = 清空回初始态（`POST /documents/reset`，破坏性清空版本历史 + 快照，**全删**）。两选一确认（对齐回滚弹窗「确定 = 更彻底」）：确定 = 连事实库一起清空（彻底归零、连门也切、实时收集砍掉）；取消 = 只清文档版本、保留事实（人还是那个人，重传/重聊可复用）。**待执行建议无条件清空**——版本没了，建议锚在旧版上脱锚（§12.3 决策四），后端 reset 与回滚一致清 pending。

**快照粒度**：按「每次生成/回滚打一个」。对话中途细粒度回滚已砍（2026-08-31，版本级够用）。

**分支**：做**线性版本 + 回滚**，不做真分支（Git 式多分支切换/合并）——单个用户一张活简历，线性够用。真分支已否决（2026-08-31）。

### 9bis. 软作废回滚（2026-08-10 实现，取代纯追加回滚）

> 2026-08-06 定稿为「切换预览 + 截断回滚」两层模型，留待生成后实现；**2026-08-10 落实为「软作废回滚」**——截断语义 + 数据全保留（不删任何数据，只打标签）。

**问题**：纯追加回滚下，「回滚到 v1」得到「v10」（版本号跳、历史行累积），用户困惑。根本矛盾是「切换浏览」和「真正回滚」混成了一个「恢复」操作。

**软作废回滚（Git reset --hard 语义 + 软删除）**：

| 操作 | Git 对应 | 语义 | 碰库 |
|---|---|---|---|
| **切换浏览（回看）** | `git checkout <commit>` | 自由看各稿历史，历史全保留 | **不写**（纯前端读产物，§11bis） |
| **真正回滚** | `git reset --hard <commit>` | 选定第 N 稿，其后稿全作废，从第 N 稿继续 | **写**（软作废） |

**关键推论**：第 N 稿基础上改，下一稿 = 第 N+1 稿（作废后从目标+1 继续），**稿号连续不跳**——满足「回滚显示目标稿号」的诉求。

**实现细节**：
- **软作废**：`resume_documents` 加 `superseded` 布尔列（2026-08-10）。`rollback` 把目标稿之后所有稿标 `superseded=True`（**数据全保留**——session/快照/原件/建议不删），目标稿回 `False` 变当前。**响应 `{version}` = 目标稿号**。
- **当前 = 非 superseded 最大 version**：`GET /documents/current` / `GET /documents/versions` 都过滤 superseded（版本面板只显示当前稿序列，被作废的看起来像被删了）。
- **下一个版本从目标+1 继续**：`create_document` 的 max version 只统计非 superseded 稿。
- **原稿数据留档**：作废稿的 session/快照/原件/建议全保留（数据资产），回看时间线聚合（§11bis）仍能看到。
- **命名**：UI 显示「第 N 稿 / Draft N」（2026-08-10，从「版本号」改为「修改轮数」）。内部 `version` 保留为可复用序号。
- **身份锚定 id（2026-08-12）**：`id` 主键是每条稿的**唯一身份**；`version` 只是显示标签——软作废后新生成**可复用**同号（回 v2 后新稿 = v3，若历史 v3 已作废则同号两条：一作废一当前）。**任何界面每个「第 N 稿」只出现一次**（取非 superseded 的当前行），作废的同号旧稿彻底隐藏；**回看按 `document_id` 精确取原件/文档**（`GET /documents/original?document_id=`，不按 version——按 version 会撞同号作废稿）。
- **前端版本面板**：只显非 superseded 稿；**当前稿行不显示「回看」**（不能回看自己）；点某稿进**回看模式**（§11bis，主区整体切当时文档+聊天）→「回滚到当前」→ 软作废回滚。**回看界面目标稿 = 当前稿时不显示「回滚到当前」**（不能回滚到自己）。
- **快照/建议**：作废稿的快照/建议**保留**（数据资产），回滚时版本变更统一结清（§12.3 决策四修订：保留 discussing、清空其余、记最终偏好），已确认建议可随新稿继续。

**与旧设计的差异**：原「截断回滚」是**硬删**（删目标后所有行 + 快照）；软作废**不删**，只打 `superseded` 标签——用户视觉上"被删了"，数据其实留着（session/快照/原件/建议都是资产，随便删没好处）。

## 11. 会话模型与对话 agent（1.2/1.3 共享底座）

> 2026-08-06 grill 定稿。1.2 优化与 1.3 生成共享同一套「会话 + 对话 agent」底座，区别只在姿态与产出。本章是 1.2/1.3 的地基。

### 11.1 会话模型：每版本一 session

**决策：每个简历版本 = 一个会话（session）。版本变更（生成 / 回滚）都是边界，各开新 session。旧 session 只读，不可续聊。**

```
V1 ──▶ V2 ──▶ V3 ──▶ V4 ──▶ V5        （版本流：线性，resume_documents）
                          ↑
                    当前 V5 的 session
                          │
                  [回滚到 V3]（数据操作）
                          ↓
               当前文档 = V3 markdown，开新 session（V3）
                          │
                 继续聊 → 生成 V4' → 开新 session（V4'）
```

- **上下文有界靠「版本切 session」，不靠剪枝**：对话历史**完整**随 session 走。上下文不会无限累积——每生成/回滚一个版本就切新 session，自然收口。**不剪枝**（剪枝被本模型取代，已否决）。
- **UI 干净轮回，历史归档**（2026-08-10 决策修订，推翻旧「UI 连续、发送有界」）：版本变更（生成/回滚/应用建议）后聊天框**清空**，干净开新轮——UI 只显示**当前 session**（id 最大那个），不聚合旧 session 历史、无版本分隔标记。旧 session 历史**归档保留**（后端照存），通过**回看模式**查看（§11bis）：版本面板点某版本 → 主区切换成该版本当时的文档 + 聊天记录（只读），可「回滚到当前」。**理由**：旧对话对用户无留存价值（记忆由 active facts 承担，§11.5），连续显示反而拖累沉浸感；干净轮回让用户一眼看到"新简历就是新的开始"。
- **记忆由 active facts 承担**：切 session 后看不到旧对话，但 agent 依然"记得"——active facts 每轮注入（§11.5）。跨 session 的记忆是事实库，不是聊天记录。
- **session 的身份跟「当前简历」走，不跟版本号**：回滚后开的新 session，`document_id` 可以是旧文档（V5→V3），它只是"这段对话发生时的当前文档"这个标签。
- **版本可对应多个 session**（V3 原 session + 回滚后重开的 V3' session）；**当前 session = id 最大的那个**，无需状态字段。
- **首个会话（尚无简历）**：`document_id` 允许 `NULL`——未上传简历时的种子 session，收信息用；生成 v1（0→1 是版本变更）即开新 session，种子封档。
- **换简历/重传不切 session（2026-08-29，推翻 S1-6）**：`reset_resume`（换简历/重传触发的重置）**不删 session**——重传是「首次上传失败」的弥补动作，仍在「首次上传」范畴内，之前的聊天要接着聊。换简历后 `current_session` 仍是旧的（id 最大），新简历的「已上传/确认」事件接着写进它，新老对话连续、血统不串。**只有真正的版本变更（生成优化简历/回滚/应用建议）才开新 session**。核爆（`reset_all`「重新开始」）仍删光 session（出厂态）。
- **历史 session 只读**：版本面板可看当时的聊天记录 + 当时的文档（免费功能），不可续聊；想基于旧版改走显式回滚（§9bis），回滚后自然开新 session，不绕路、有确认、血统干净。

**为什么不支持"切回旧 session 续聊"**：那会打破版本流的**单血统不变式**——旧 session 注入的是旧"当前简历"（如 V3 markdown），而全局当前是 V5。继续聊 + 生成会撞三难：① 追加成 V6 但基于 V3，血统是假的、版本号说谎；② 静默截断到 V3，绕过显式回滚确认；③ 留两条线 = 分支（明确否决）。版本生成即封档，历史只读，是最干净的形态。

### 11.2 会话存储：SQLite 表（UI 真相源）+ 图 checkpointer（agent 工作记忆）

**决策（2026-09-10 迁移定稿）：`chat_sessions` + `chat_messages` 表是前端 UI 与历史的唯一真相源（对话原文 + 系统气泡，Append-only）；对话 agent 的工作记忆（恢复上下文 + 折叠）由 deep agent 图的 checkpointer 承担。二者是同一对话的两份投影，正交。**

| 表 | 列 | 说明 |
|---|---|---|
| `chat_sessions` | `id` / `document_id`（index，可 NULL） / `created_at` | 一个会话 = 一段"从版本 A 到版本变更"的对话。`document_id` = 会话开始时的当前文档 id（唯一身份，2026-08-12 A3 从 `document_version` 迁来；种子会话为 NULL） |
| `chat_messages` | `id` / `session_id` / `role` / `content` / `seq` / `created_at`（+ `kind` / `ref_document_id`，2026-08-20/21，仅 event 行用，见 DATABASE.md） | 会话内的消息，`seq` 保证顺序；**UI 历史读它**（原文 + 系统气泡） |

**为什么表仍存对话原文、不复用 checkpointer 当 UI 源**（2026-09-10，查官方推荐做法后定）：
- **SummarizationMiddleware 会折叠**——checkpointer 里较早的消息被摘要替换（原文丢失/移进 offload 文件），喂 UI 会丢原文。Append-only 表才保得住 UI 要的完整历史。
- 官方最佳实践即「checkpointer 服务 agent 工作记忆，UI 历史单独用一份 append-only 表」；本地单用户，一份表成本可忽略。
- **系统气泡（event，带 kind/ref_document_id）本就不是对话记录**，继续留表——`latest_event_kind` / `latest_event_ref_document` 读它（阶段判定 / 回滚溯源），回看模式也读它。
- **双投影一致性**：撤回（取消重新输入）时，表删最后一条 user 消息，checkpointer 也精准删同一条（`RemoveMessage`，甲方案）——否则 agent 下次恢复上下文还看得到已撤回的话，记忆与 UI 脱钩。中断（cancel）与回退（新 session 天然隔离）无需额外处理。

### 11.3 聊天请求：服务端持有唯一历史，增量式

**决策：聊天从「客户端带全量历史（无状态）」改为「增量式」——服务端是历史的唯一持有者。**

```
POST /chat { session_id, message }
  服务端：DB 读全量历史 → append 用户消息 → 持久化 → 跑 agent → append 助手回复 → 持久化 → 返回
```

- 重启后聊天完整还原（挂载时按 session 拉历史）；客户端无状态。
- **不会出现"UI 历史 vs DB 历史"两份真相打架**——只有一份，服务端持。
- **事件消息也进 chat_messages**（2026-08-10 落地，此前是死代码）：上传/确认/回滚/生成等系统事件（"已上传简历：xxx.pdf"、"已回滚到 vX"）由 service 层顺手写进当前 session——`record_current_event` 统一入口（无 session 自动开种子）。事件以 **event 角色**存储（区别于 user/assistant）：前端据此渲染**系统气泡**（居中灰条，不回显用户气泡）；chat.py 注入 agent 前**过滤 event**——系统动作无需 agent 处理，不污染 LLM 上下文。回看模式（§11bis）能看到事件，聊天上下文保持干净。
- **系统气泡三档（2026-09-01）**：agent/系统的非对话动作统一走「系统气泡」一族样式，**不落进聊天气泡伪装成"助手说话"**。分三档，前端按 `chat_messages.kind` 判定（不靠文案匹配）：**事件灰条**（成功事件：`upload`/`generated`/`rolled_back`/`suggestion_hint` 建议提示…）；**错误红条**（失败/约束报错：`error_*`）；**系统卡片**（带按钮的结构化块：事实冲突卡）。**错误也留痕**：`AppError` 全局 handler 收口失败时顺手把错误事件落库（瞬时护栏/协作式信号置 `record_event=False` 例外），成功/失败同一真相源——此前是「成功后端记 + 失败前端 `pushAssistant` 拼」的双源。**2026-09-08删「去生成」应急卡**—— 后零文档也能生成，那堵「还没有结构化简历」的死路已消解，`upload` 统一落事件灰条。

### 11.4 对话 agent：自己问自己记（工具调用）

**决策：对话 agent 用**工具调用**写事实——agent 自主决定问什么、记什么；「判断在 agent、处理在代码」，不设额外的"事实整理 agent"层。**

- **工具调用（而非结构化输出）**：把 `record_facts` 工具交给 agent，工具描述/prompt 写清"何时该记"（相关、稳定事实；闲聊不记）。agent 自己什么时候想记、就什么时候调。用户明确偏好工具调用的形态（"自己问自己记更有结构"）。
- **工具循环住图（2026-09-10 修订）**：对话 agent 从「service 层手写 while 循环」迁到 deep agent 图（`app/graphs/chat.py`，`create_deep_agent`），工具循环在 LangGraph 图内，符合「工具循环住图」的铁律。业务工具（`record_facts`/`suggest_improvements`/`update_suggestion`/`apply_suggestions`/`generate_resume`/`refine_direction`/`commit_direction`/`query_market`/`supersede_fact`）在 `app/services/chat_tools.py` 声明为真函数，函数体直接调 service 领域逻辑（写库/冲突检测仍在 service）——graph 不 import 业务 service（工具/重建 prompt 由 service 装配时注入占位）。安全阀由图的循环上限承担（deepagents 内建），不再有手写 `MAX_TOOL_ROUNDS = 40`。每轮 system prompt 由自定义 `wrap_model_call` middleware 重建（面板四栏最新，§12.6 D10）。
- **`record_facts` 返回值如实**：工具执行后返回 `记了 N 条 / 跳过 M 条（已存在）/ 冲突 K 条` 给 agent——否则 agent 以为记了实际没记（幂等跳过），后续可能重复问。
- **为什么不再加一层"事实整理 agent"**：冲突/去重是**确定性逻辑**（§4 统一冲突检测，`confirm_facts` 共享 service 已实现），用 LLM 重做是"用 LLM 重写一段代码"——慢、不稳、还可能自作主张。真正有活的判断（收录判定 + 真伪冲突裁决）只有对话 agent 能干（它要问用户："你之前说过雅思 4.5？"），第二个 agent 没有对话上下文。**判断在 agent、处理在代码**，不是多一层 agent。

**对话挖掘 → 入库**：agent 调 `record_facts` → service 执行 `confirm_facts`（统一冲突检测）→ 幂等重复跳过（agent 不被打扰）/ 真伪冲突不自动裁决、返回给 agent → agent 对话反问用户 → 用户答 → 再写入。

### 11.5 每轮注入：agent 的上下文构成

**决策：每轮组 prompt 注入「active facts 全量 + 偏好（判定标准）+ 当前完整简历」，作为只读背景。**

- 这三样**不剪枝、全量注入**（单用户几十条事实、一份几千字简历，无压力，不用向量检索）。
- 理由：**缺口感知**的前提（agent 要知道"技能这块还空着"才能往那问）；**避免重复问**（用户说过"2021-2024 南大本科"就不该再问学历）；**避免记重**（写之前瞥一眼已有事实）；**偏好对齐**（"不量化"进上下文，问的方向才对）。
- 注入方式：塞进 system prompt（只读背景，不是工具——用工具去查反而多一轮、还要 agent 记得调）。
- 这就是「上下文构成 = UI 一致完整历史 + active facts + 当前简历 + 偏好」的落点。

### 11.6 姿态：采集 / 优化 = 同一 agent 两种对话姿态

**决策：对话 agent 是唯一的对话角色（沿用原「一个简历 agent」的定义），采集与优化是它同一张嘴的两种姿态。生成不是对话姿态——它是文档任务（§13）。**

| 姿态 | 产出 | 工具 |
|---|---|---|
| 采集 | 对话文本 + `record_facts` 调用 | 记事实 |
| 优化建议 | 对话文本 + 建议清单（结构化） | 记事实 + 出建议 |

- 两种姿态共享工具、事实库、注入（§11.5）；区别只在产出形态。
- 「一个 agent」的真义 = **对话只有一种**（聊天时既能收信息也能给建议）；**生成从来不是对话姿态**（CONTEXT.md 里「生成简历」是独立术语，从未被划进"一个 agent"）。

### 11.7 采集姿态升级：缺口驱动 + 层层深挖 + 边聊边嗅矛盾（2026-08-20 定稿）

**决策：把采集姿态从「被动记录」升级为「主动采集」——后端算缺口信号（硬）注入 prompt，agent 按缺口层层深挖（软），并在聊天中边聊边嗅矛盾。笔法借鉴 mattpocock/skills 的 `grilling`（决策树 + frontier 一轮问清）与 `domain-modeling`（边聊边挑刺/交叉验证）。**

**背景问题**：旧 prompt 只教 agent「遇到就记」（`record_facts` 的收录判定），没有「搜集到什么程度算够、缺什么主动补什么」的驱动。结果 agent 是「你聊到哪我记到哪」，不主动补全信息；就业方向等关键槽位常空着，到生成/投递时才发现没方向。

#### 11.7.1 缺口是二维的：「有没有」（硬）×「深不深」（软）

- **硬维（有没有）**：关键槽位是否填了。这层**后端可算**，是注入 prompt 的「缺口信号」。
- **软维（深不深）**：每个已填槽位的**颗粒度够不够做简历**。这层是语义判断，**交给 agent**（C 方案：后端别硬编码语义）——
  > "想做软件开发" = 有但太浅（做不了简历靶子）→ 挖"前端还是后端？"→ 再挖"React 还是 Vue？"。"会 Vue" → 挖"到什么程度？有作品吗？"。"做过一年老师" → 挖"什么老师？教哪科？这一年成就？"。

#### 11.7.2 分工：后端报「哪里缺」（硬），agent 定「怎么挖、够不够深」（软）

- **后端（硬）= 缺口计算服务**：读 active facts，判每个关键槽位**有没有**（`missing` / `has`，纯有无二态），产出一段「缺口报告」文本注入 system prompt（与 facts/简历同机制，§11.5）。
  - **只判有无，不判深浅（2026-08-20 定稿选 a）**：深浅是语义判断，后端硬编码关键词列表（如"方向含不含技术栈词"）脆且易误判；facts 每轮全量注入、agent 本就看得到，「够不够深」全留给 agent。后端只给「空/非空」这个铁的事实。
- **agent（软）= 深挖 + 嗅矛盾**：照缺口报告（哪些槽位空），**从缺的/浅的槽位优先**，借 `grilling` 笔法层层追问（一次一层、一个问题、给推荐答案），挖到「简历够用深度」即换下一槽；同时借 `domain-modeling` 笔法**边聊边嗅矛盾**（见 11.7.4）。**「够不够深」由 agent 对照注入的 facts 全貌自判**——这正是它的语义强项。

#### 11.7.3 「简历够用深度」收敛标准（够用即停，不无限深挖）

| 槽位 | 优先级 | 够用深度（挖到此即换槽） |
|---|---|---|
| **求职方向** | **第一** | 具体岗位 + 技术栈/方向细分 + 程度/年限（如"前端·React·3年"）；够了即触发 `refine_direction` 出方向提案 |
| 工作经历 | 次 | 每段：做了什么 + 量化成就（不只"在哪、什么岗"） |
| 技能 | 次 | 每项：掌握程度 + 作品/佐证（不只"会 X"） |
| 教育 | 低 | 基本事实即够（学校/专业/学历/时间），不深挖 |

深挖**收敛不无限**：挖到「够用」线就停（跨界的"老师会 Vue"不必挖到底）。这是收敛边界，防采集聊成无止境盘问。

#### 11.7.4 矛盾辨识：双闸门（当前 session 当场嗅 / 跨 session 落笔兜）

用户说的可能前后矛盾，**不能照单全收**。矛盾分两类，各归一道闸门（语义判断全在 agent，service 不做语义）：

- **闸门 1（聊天中，agent 边聊边嗅）——主防线**：agent 对照**当前对话 + 每轮注入的 facts 全貌**自查一致性。发现不搭（如"这段是当老师" + "这期间做前端 200 万用户"）→ **当场反问澄清**（"是转行了，还是教学之外的私活？"），问清楚再决定记不记。**当前 session 内解决，不落笔。** facts 每轮全量注入（§11.5），agent 天然看得到旧事实——跨 session 的软矛盾也由这道闸门在注入的 facts 里嗅。
- **闸门 2（落笔时，service 冲突检测）——兜底**：兜**硬冲突**（同字段不同值，如"雅思 7.5 vs 4.5"）——`record_facts` 返回 `conflicts` → agent 反问。**保持硬冲突范围**，不扩到语义软矛盾（service 不做语义判断，这是 C 方案红线）。

**火候（定稿）：偏松但有底线**——明显不搭（同期角色直接冲突）当场反问；存疑但讲得通的（跨界/兼职）先记下、不追着问。采集阶段目标是「先把信息挖全」，审太紧会把聊天聊成盘问。

#### 11.7.5 落地清单

- **后端**：`app/services/facts.py`（或新 `info_gaps.py`）加缺口计算 `compute_info_gaps(facts) -> str`（关键槽位纯有无二态）；`chat_tools.build_deep_system_prompt` 注入 `{info_gaps}`。
- **prompt**：采集段重写（现落在 `resume_agent_deep.md` 的指向 + `collect` skill；旧名 `resume_agent.md` 已随 拆分删除）——使命加「主动把关键信息补齐（缺口驱动，方向优先）」；加「深挖追问」（借 grilling：一次一层、一个问题、给推荐答案、够用即停）；加「边聊边嗅矛盾」（闸门 1 笔法 + 火候）。
- **工具**：`record_facts`/`refine_direction` 不变（闸门 2 / 方向提案复用现有）。
- **测试**：缺口计算单测（各槽位有无二态 + 方向槽位按「目标岗位：」前缀判 + 渲染只列缺项）；prompt 注入含缺口报告。

### 11.8 分阶段主动引导：回来时不等用户开口（2026-08-20 定稿）

**决策：聊天开场从「前端写死的静态欢迎语」升级为「分阶段的主动引导」——阶段判断由后端定（硬），引导话术由 agent 生成（软，路线 C 混合）。阶段切换的「关键时刻」主动说一次，平时打开不刷屏。**

**背景问题**：旧开场是一条固定 i18n 欢迎语（`resume.welcome`），不区分阶段、agent 从不主动开口。但每个阶段用户回来，该做的事不同——不该等用户先开口，而该把「能做的事、能拓展的方向」先摆出来给思路。

#### 11.8.1 四个阶段 + 各自的引导重点

| 阶段 | 判定（后端硬判） | agent 开场该说 |
|---|---|---|
| **冷启动** | 无简历文档 且 无 facts | 引导上传简历，或直接把经历聊完整。**模板化**（没数据可个性化，不烧 token） |
| **已上传** | 有简历文档，未生成过新版本（**确认入库后**，见 §11.8.3） | **先聊求职方向**（想投什么岗位/城市/技术方向），方向聊透后再提优化讨论范围（结合缺口报告 §11.7）；**不先点评、不先抓优化点** |
| **已生成** | 生成/改写过新版本后 | 回述这版改了哪些点、评价当前简历，**问用户改得怎么样**（先不主动提新优化点，等用户表态再顺着聊） |
| **已回滚** | 回滚到旧稿后 | 说明回到了哪稿、后续怎么调 |

#### 11.8.2 路线 C：阶段判断硬、话术软

- **阶段判断（硬，后端）**：读 `latest_document`（有无简历/版本）+ facts（有无）+ 当前 session 的最近一条 **event**（刚发生的动作）→ 定当前阶段 key。复用 §11.7 缺口信号告诉 agent 该补什么。
- **event 带结构化类型（2026-08-20 定稿，不靠文案匹配）**：`record_current_event` 加 `kind` 参数（`upload`/`generated`/`rolled_back`/`direction_changed`/…），`chat_messages` 加 `kind` 列（event 行用，init_db 迁移补列）。阶段判定读 kind，**不匹配中文文案**——文案匹配是埋雷（apply.md §7.3 铁律：不靠猜文案关键词，靠结构化标记）。
- **话术生成（软，agent）**：除冷启动走模板外，其余阶段跑一次 agent，结合当前 facts/简历/缺口/**刚发生的动作**生成个性化引导（真能点出「你简历工作经历那段偏薄」）。冷启动无可个性化内容，直接用模板文案（省 token、即时）。
  - **「改了哪些点」的数据源**：`list_applied_for_document(doc_id)`（§12.3 软标记）——已生成 = 当前版应用的 confirmed 建议；已回滚 = 被回滚覆盖的那版的 applied 建议。不给 resume_documents 加 changes 列。

#### 11.8.3 触发时机：阶段切换的「关键时刻」，不刷屏

- **只在阶段刚切换后主动说一次**：生成/改写保存、回滚、**上传确认入库**——这些动作已写 event 气泡（`record_current_event`），且都伴随「开新 session」（§11.1 干净轮回）。**新 session 的第一条助手消息 = 该阶段的主动引导**，替代原静态欢迎语。
- **「已上传」阶段的触发点 = 确认入库，不是上传本身（2026-08-21 修正）**：上传成功时 facts 还没抽出来，缺口报告是空的、agent 没料可判该往哪引导。故 `record_current_event` 的 `kind="upload"` 挂在**确认入库**（`confirm_extract`，facts 已进资料集），上传事件**不带 kind**——否则引导会对着空 facts 空谈。
- **动作时刻生成 + 落库（2026-08-23 修订，修复「每次切页重生成」漏洞）**：引导词在各动作点**生成并落库为当前 session 的一条 `assistant` 消息**，前端 `loadChatHistory` 只「读」历史、不再触发生成。原实现（读时生成、不落库）会让每次切页回来都重新生成，违反「说一次」。生成失败（没配 key/网络断）**不抛异常**（动作已成功，报错会造成「动作成功却显示失败」的脏状态），而是落一条诚实说明的 `assistant` 消息（「模型连不上，可去设置检查或直接提问」）。
- **冷启动欢迎语落库（2026-08-30，修「欢迎语消失」）**：冷启动（无 session）时前端本地显示 i18n 欢迎语 `resume.welcome` 兜底；一旦上传开了种子 session，`loadChatHistory` 用后端消息覆盖，纯前端的欢迎语就会消失。修法：`open_session()`（无参 = 种子会话）把欢迎语**落库**为第一条 `assistant` 消息（后端 `_WELCOME_ZH/_WELCOME_EN` 与前端 i18n 逐字一致，改需同步）。版本 session（`open_session(document_id=...)`）不落——版本变更是干净轮回，由各阶段开场白替代。前端冷启动兜底仍保留（无 session 时仍本地显示，不重复落库）。
- **平时打开/切回不生成**：引导已落库为 `assistant` 消息，`loadChatHistory` 读历史自然带回来，不重复生成。冷启动（无任何 session）例外——那是第一天，前端显示静态欢迎语。

#### 11.8.4 落地清单

- **后端**：`chat_messages` 加 `kind` 列（event 行的结构化动作类型）+ `record_current_event` 带 `kind`；新增「开场引导」service（`opening.py`：`generate_opening_content` 生成 + `persist_opening` 落库为当前 session 的 assistant 消息，注入 facts+简历+缺口+刚发生动作+上一版改动清单）；各动作（生成/应用建议/改写/修复排版/回滚）在 `record_current_event` 后调 `persist_opening`。**无 `/chat/opening` 端点**（2026-08-23 删）。
  - **agent 工具触发的版本变更 → 跳过 `persist_opening`（2026-08-25 §12.6 D4）**：agent 工具在对话中产出新稿时，用 agent 自己那句回复当新 session 引导（更贴上下文 + 省一次 LLM），不跑 opening agent。`persist_opening` 仍服务于 **UI 按钮**触发的版本变更（开始改按钮/回滚/生成确认，无 agent 在场）。**2026-09-09**：`apply_suggestions` 工具不再直接写库，改走统一图出预览（人门确认才落库）——「版本变更」这个持久化边界由 `generate_confirm` 承担，opening 落库也随之在 confirm 里发生。

### 11bis. 回看模式：历史归档的只读查看（2026-08-10）

**决策：版本变更后旧 session 历史归档保留，通过「回看模式」只读查看——回看 ≠ 回滚，是两种状态。**

- **回看**（纯读）：版本面板点某稿 → **主区整体切换**成该稿当时的文档 + 聊天记录。文档优先原生预览（`GET /documents/original?document_id=N` 拉该稿原件重建 blob，**2026-08-12 按 id 精确取**——不按 version 撞同号作废稿），无原件落 Markdown；**有排版层 HTML 的稿（2026-08-13）优先 iframe 渲染该稿的 `html`**（回看显示当时版式）。**不改任何后端状态**，退出回到当前稿。
- **聊天按时间线聚合**（2026-08-10 修）：**不用 `document_id` 过滤**——那个字段是「会话开始时的文档」，种子会话（NULL）/ 回滚后新开会话（绑定回滚后文档）都不归目标稿。改为：稿按 `created_at` 排序定「生效区间」（`[该稿, 下一稿)`），会话按 `created_at` 落入所在区间的稿，合并该稿区间内所有 session 的消息（版本分隔标记串联）。前端拉 `GET /documents/versions?all=true`（含软作废稿，时间线边界）+ `/sessions` 全量自己算（数据量小）。
- **回滚**（数据操作）：回看界面里「回滚到当前」按钮 → 确认（未定论建议去留提示）→ 走 `POST /documents/rollback`（软作废 + 新 session + 聊天清空 + 版本变更统一结清）。**目标稿 = 当前稿时不显示该按钮**（不能回滚到自己，2026-08-12）。回滚逻辑从版本行**移进回看界面**——版本行只留「回看」入口（当前稿行不显示），避免误触。
- **为什么回看要带"当时的文档"**：回看某稿 = 看"那稿简历长什么样 + 当时聊了什么"，两者必须一致才有意义。生成/回滚稿无原件 → 显示当时的 Markdown（`resume_documents` 每行都存 markdown，天然可回看）。
- **前端状态**：store 的 `review` 字段（非 null = 回看中）持有该稿文档 + 消息，与当前对话状态（messages/sessionId）解耦——回看不污染当前会话。

## 12. 优化建议流（1.2）

> 2026-08-06 grill 定稿；**2026-08-10 落库升级**：建议组从「聊天暂存」改为「落库对象」（状态机 pending/confirmed/rejected/discussing），操作收敛到**三栏面板**（左待定 / 右已确认 / 正在聊），聊一聊由 agent 看得见面板后针对性讨论、讨论即定论。**2026-08-12 四栏升级 + 策略反转**：加「已拒绝」灰栏（版本内可撤回）、待定项默认展开、开始改门控、偏好延迟记录、版本变更**保留 discussing**。**2026-08-13 面板体验 + agent↔面板同步**：左右 1:1、统一建议卡（原文划线 → 新改法）、删头部总数；`propose_suggestion` 工具 + 聊天内提议选项框（决定权在用户）。**2026-08-25 优化点操作权**：推翻 S4-1/S4-2 禁令，接受/拒绝/聊一聊/撤回 +「开始改」全部开放给 agent 直接操作（§12.6），废提议卡 + `propose_suggestion`，`decide_suggestion` 改名 `update_suggestion` 加 discuss/retract。判定标准与偏好库见 §5。

### 12.1 流程总览

```
[触发] 用户"帮我优化一下" / agent 主动提议"技能那块可量化，要看建议吗？"（双通道）
   ↓
[优化姿态] 读：当前文档 vN + active facts + 偏好（§11.5 已注入）→ 对照判定标准（§5）出建议清单
   ↓
[落库] suggest_improvements 产出即落库 pending（optimization_pending 状态机，§12.3）→ 面板左栏待定
   ↓ 处理（面板四栏 或 聊天口头，二者等价，agent 直接操作 §12.6）
[左栏默认展开] 每条显示标题+内容+三按钮：接受（→confirmed）/ 拒绝（→rejected 灰栏）/ 聊一聊（→discussing）
[右三栏每条可撤回] 已确认 / 正在聊 / 已拒绝 → 回待定（版本内）
   ↓ 聊一聊 / 聊天里口头表态
[agent 直接裁决] agent 注入面板四栏全貌（§11.5），理解用户指代 → update_suggestion 直接改状态
   ↓ 裁决（讨论即定论，不二次确认）
[accept/reject/refine/split/discuss/retract] 确认→右栏 / 拒绝→灰栏 / 细化→内容更新回待定 / 分裂→原条+新条待定
   ↓ "开始改"（收敛确认，门控：有待定禁用、有 discussing 弹确认；agent 或按钮都可触发）
[文档任务·增量改写] 右栏已确认的建议进 prompt → 只动选中的 → 新稿（vN+1）→ 版本变更统一结清
   ↓ 应用完成 = 版本变更
[开新 session] apply（vN→vN+1）是版本变更 → 开新 session，事件写进新 session（§11.3）
   ↓ 版本变更统一结清（2026-08-12 策略反转）
[保留 discussing / 清空 pending+confirmed+rejected / 清 rejected 时延迟记最终偏好]
```

### 12.2 建议 schema（六类）

```json
{
  "id": "sug-1",
  "type": "quantify",
  "target": "工作经历>腾讯>第2条",
  "original": "负责维护系统",
  "suggested": "优化查询性能，响应时间降低40%",
  "reason": "成果导向：有量化、有强动词",
  "severity": "high"
}
```

- **`type`（六类）**：`quantify` 量化 / `word_choice` 用词 / `structure` 结构 / `fill_gap` 补缺 / `job_relevance` 岗位相关 / `highlight` 卖点。对齐 §5 的 LLM 判定维度（量化/用词/板块结构/卖点/岗位相关性）——判定标准怎么评，建议就怎么分。
- **`target`（指向文档哪处）**：增量改写（§12.3）精确落点的前提。用 Markdown 锚点定位（`工作经历>腾讯>第2条`），文档任务拿到才能"只动这里"。
- **`original` + `suggested`**：原文 vs 建议改法，用户对照看、多选时心里有数。
- **`reason`**：为什么这么建议（引用判定标准，如"成果导向"），用户拒绝/接受有依据。
- **`severity`**：高/中/低，用户先看重要的。

### 12.3 优化点面板（四栏，建议收件箱）

**决策（2026-08-10 落库升级 + 2026-08-12 四栏升级）：建议组从「聊天暂存」改为「落库对象」（`optimization_pending` 完整状态机），操作收敛到**四栏面板**——这是"建议"的唯一持有形态，聊天流不再渲染建议卡片。面板跟稿走（§12.4 决策四）。**

- **四栏布局**：
  - **左栏 = 待定（pending）**：suggest_improvements 产出即落库 pending。**每条默认展开**（2026-08-12：不再点击才展开）：统一建议卡（type + target + 原文划线 → 新改法）+ 三按钮「拒绝 / 接受 / 聊一聊」横排。
  - **右栏上 = 已确认（confirmed）**：接受后移入，是"下次改进方向"，「开始改」应用这批。
  - **右栏中 = 正在聊（discussing）**：点聊一聊后移入，agent 讨论中（用户去聊天框直接提问，无引用——agent 注入面板四栏全貌，§11.5，自然理解指代）。
  - **右栏下 = 已拒绝（rejected，灰栏）**：拒绝后移入，**版本内可撤回**——给用户一个机会在本版本内把拒掉的建议拉回来重新决定（2026-08-12）。
  - 四栏背景淡色半透明：左红 / 已确认绿 / 正在聊蓝 / 已拒绝灰；每栏标题旁显示本栏数量。
- **左右 1:1 布局（2026-08-13）**：左待定 / 右三态组等宽（`.suggestion-col-group` flex 2.2 → 1），面板加宽 880px——待定区承载更多内容。**2026-08-13 再调整**：**已拒绝挪到左下**（左 = 待定 3 : 已拒绝 1，上下堆叠；右 = 已确认 : 正在聊 1:1）——右栏从三栏变两栏、每栏更宽不挤。
- **滚动修复（2026-08-13）**：`.suggestion-col`/`.suggestion-col-group` 补 `min-height: 0`（flex 子项不压缩则内部列表 `overflow-y: auto` 不触发，底部内容被面板 `overflow:hidden` 裁掉）——条数多时每栏内部独立滚动。**全局窄滚动条（2026-08-13）**：从建议面板样式推广到全系统——全局 `*::-webkit-scrollbar` 6px 圆角半透明，thumb 默认透明（隐藏）、任意滚动元素 hover 时淡入、hover 滚动条本身加深；覆盖所有滚动容器（主区/左栏/预览/面板/抽取卡/资料集/建议面板 + Mantine 控件）；聊天区 `.chat-messages` 保持隐藏（刻意，特异性更高覆盖全局）；Firefox 兜底 `scrollbar-width: thin`。

- **收起/展开（2026-08-13）**：统一建议卡加折叠——**待定默认展开、右三栏默认收起，都可手动点开/收起**（卡头右侧 ▾/▴ 独立按钮）。收起态 = 两行（sev+type+target 一行 + 改法截断一行，不点开也能瞥一眼方向）。聊天提议卡不折叠。
- **撤回常驻卡头（2026-08-13）**：右三栏「撤回」移到卡头右侧、折叠按钮旁（`headActions`）——**收起/展开都能直接撤回**（不再藏在展开区的 actions 里，收起态也操作不了撤回的不便已消除）。
- **统一建议卡（2026-08-13，治"左右显示不一致"）**：左右栏共用 `SuggestionCard`——元素序统一（sev 点 + type 徽标 + target + **原文划线 → 新改法** + reason）；右栏不再只显示改法、丢"在哪/作用域"。**删头部总数 pill**（分栏后每栏已有计数）。
- **撤回（2026-08-12）**：右三栏（已确认 / 正在聊 / 已拒绝）每条一个「撤回」按钮 → 回待定。撤回是版本内操作，不影响版本变更统一规则。
- **角标优先级级联（2026-08-12）**：优化点胶囊右上角角标 = 当前最该做什么的信号——有待定 → 红角标（pending 数）/ 待定清空有正在聊 → 蓝角标（discussing 数）/ 都无 → 绿角标（confirmed 数）/ 全 0 无角标。事件驱动刷新（挂载 + 关键操作后），不轮询。
- **去重**（修旧 bug——同一建议可无限次收录）：`accept` 校验状态，已 confirmed/rejected 的拒绝再接受（后端兜底）。
- **落库状态机**：`pending → confirmed / rejected / discussing`；裁决（`decide_suggestion`）从 discussing 定论：accept→confirmed、reject→rejected、refine→内容更新回 pending、split→原条 pending + 新条 pending（`split_from` 关联）。
- **积累 → 一次性执行**：右栏 confirmed 攒批（可跨多轮、跨 focus）→ 用户说"开始改" → confirmed 建议放进 prompt → 文档任务增量改写 → 新稿。
- **开始改门控（2026-08-12）**：还有**待定**（pending）→ 「开始改」禁用（必须先处理完待定）；待定清零 → 放行。还有 **discussing 未结论** → 点「开始改」弹确认（「还有 N 条聊一聊没结论，是否继续生成新版本？」）→ 确认继续（聊一聊保留到下一版本）。
- **面板跟稿走（决策四修订，2026-08-12 策略反转）**：**版本变更（开始改 / 生成确认 / 回滚）统一结清——保留 discussing（聊一聊的内容留到下一版本继续聊，是否适合新版由用户判断）；结清 pending/confirmed/rejected**（定论项锚在旧稿上脱锚）；清 rejected 时延迟记最终偏好（§12.5）。`reset`（回到空态）仍**无条件全清**（含 discussing）。回滚前前端提示未定论建议的去留。
- **结清 = 软标记，不物理删（2026-08-20 大雷修复，推翻物理删除）**：旧实现 `clear_by_status` 是 `session.delete(row)` **物理删行**——丢了「这条建议在哪个版本产生、在哪个版本被应用/清掉」的溯源，回滚回来查不到「上一版改了哪几点」。改为**软标记 + 全留存**（单简历修改记录量级小，无膨胀压力）：
  - `status` 加终态 `applied`（已应用进新稿）/ `archived`（版本变更被结清但未应用，如被清的 pending/rejected）；
  - 已有 `document_id`（产生于哪个版本）；**加 `resolved_in_document_id`**（在哪个版本被应用/结清；NULL = 仍活跃）。
  - 版本变更结清 = 把当稿活跃的 pending/confirmed/rejected 软标 `applied`/`archived` + 记 `resolved_in_document_id`，**不删行**；discussing 保留（仍活跃、不动）。
  - **面板只读活跃建议**（`resolved_in_document_id IS NULL`），视图不变。
  - **溯源全留**：哪版产生 / 哪版应用 / 改了哪几点全在——这正是 §11.8「已生成/已回滚」引导说「这版改了什么」的数据地基：**不给 resume_documents 加 changes 列**，「这版改了哪些点」直接查 `status=applied AND resolved_in_document_id=这版` 的建议（一份数据两处用，不跨线复制）。
- **聊一聊 = 讨论即定论**：agent 讨论后直接裁决（accept/reject/refine/split），不二次确认——因为「开始改」时还有收敛确认兜底（用户能看到最终要应用的 confirmed 清单）。
- **agent 主动提议 → 用户确认（2026-08-13，agent↔面板同步）**：agent 把讨论接近定论的建议草拟成新改法，调 `propose_suggestion` 工具暂存提案（服务端单例，不落库）→ `/chat` 响应带 `proposal` → 前端在聊天里渲染**选项框**（统一建议卡 + 「收进已确认 / 继续聊」）：
  - **收进已确认**（`proposal/confirm`）→ 内容更新 + 状态 confirmed（清提案）。
  - **继续聊**（`proposal/dismiss`）→ **草稿保留**：内容更新到建议上 + 状态保持 discussing（面板「正在聊」区显示最新思路），用户可继续聊、也可再提议。
  - **用户已明确同意**（"就按这个改吧/收了吧"）时 agent **不提议**，直接用 `decide_suggestion(accept)`（讨论即定论）。
  - 决定权在用户：agent 只草拟、不直接落定。任一改状态动作（accept/reject/decide/retract/版本变更/reset）后提案清空（防陈旧——旧提案不再透传成孤儿卡片）。
  - 提议卡不持久化：agent 的文字话术已落库，选项框是增强 UI；刷新后消失，但确认/继续聊的结果已在面板反映。
- **建议卡只保留**「有产物要用户过目、且面板承载不了」的：事实冲突卡 ✅ 留（新旧两条对比、无面板承载）；**建议提议卡 ❌ 废**（面板「正在聊」栏就能显示）——建议这条线全部走「面板显示 + 文字确认」。（**方向提案卡也于 2026-08-25 废**——方向口头化，见 apply.md §11.2bis，无面板承载改为口头确认 + 后端卡门。）
- **落库持久化**：`optimization_pending` 表（状态机 + split_from），重启不丢、跟聊天历史同源、回看能看到当时的建议。

### 12.6 优化点操作权（agent 直接操作面板，2026-08-25 定稿）

**决策：推翻 2026-08-13 的 S4-1/S4-2 禁令（裁决只许 discussing），把「决定权在用户」从「操作权只在鼠标」改回「拍板在用户、执行在 agent」。原则：看出该改要主动说（推荐义务）；动手前先问（得准才动手）；用户表态后（口头 or 面板）直接执行。**

**2026-08-29 修订——「面板 = 工作记事本」+ 分级自主度（grill 定稿）**：优化点面板是聊天 agent 的**工作记事本**，聊天围着它转、agent 高频操作它。操作阈值从「用户有没有表态」改为「**动作的风险**」分级：

| 动作 | 目标状态 | agent 自主度 |
|---|---|---|
| 待定 / 正在聊（互转，聊哪条挪哪条） | pending / discussing | **随便动，不问** |
| 落新点到待定（抓一轮 / 聊中自然聊透） | pending | **直接落，不问** |
| 确认（收进「已确认」） | confirmed | **敲定句 + 用户确定口吻** |
| 拒绝（进灰栏，版本变更记偏好） | rejected | **敲定句 + 用户确定口吻** |

- **优化是默认姿态，但方向优先（2026-08-29 修正）**：有简历在手，优化不是"被点名才做"的活。但**求职方向聊透是抓优化点的前置门槛**——方向没聊透就先聊方向（第一优先），聊透后才抓优化点。方向聊透 + 改版回来后抓一轮改进点直接落待定，作为这轮工作底稿；对话围绕点展开，聊中随手继续收。
- **敲定收口**：聊透一个点，agent 敲定一句「我的结论是这样，你认不认？」，用户认了才收进「已确认」。
- **力度克制**：循序渐进（2~3 个立得住的点先落，宁可少）；符合事实（锚在简历实际内容）；没点不硬抓（确实没有值得改的就明说，不产凑数建议）。

**背景问题**：旧模型下 agent 的工具面是面板动作面的真子集——面板能接受/拒绝/聊一聊/撤回，agent 一个都做不了（`decide_suggestion` 锁死在 discussing，`optimization.py:120-122`）。用户在聊天里说「第 2 条接受」，agent 只能调 `decide_suggestion` 收到一句「还在待定，先点聊一聊」→ 把用户踢回面板点鼠标。且「聊一聊」完全断链——用户说"第 3 条展开讲讲"，agent 讲了，面板里那条还躺在待定栏，面板与对话脱节。`propose_suggestion` 提议卡（聊天内「收进已确认 / 继续聊」）因入口窄（只对 discussing）几乎不可见，还拖着 6 处 `clear_proposal` 防腐逻辑。

**决定**：

1. **推翻禁令（D1）**：`decide_suggestion` 状态守卫从「只许 discussing」放宽到「只要还活跃（`resolved_in_document_id IS NULL`）就能裁」。
2. **四个状态动作全开（D2）**：接受/拒绝/聊一聊/撤回全走 `decide_suggestion` 一个工具（见下），不加二次确认卡（都可逆、触发条件本就是用户已表态）。关键收益：聊一聊断链接通，agent 一边答一边挪进「正在聊」，面板跟得上对话。
3. **开始改做成工具 `apply_suggestions`（D3）**，但**先问**（纯文字，不发卡）。继承「有待定就禁用」门控，由 agent **用嘴清门**：还有待定不直接改，逐条念给用户、用刚开放的 accept/reject 清掉，清空后再问"现在改？"。**2026-09-09**：本工具改为折进统一简历图——调 `generate_preview(apply_confirmed=True)` 出预览、人门确认才落库，不再直接写库。
4. **孤儿回复修复（D4）**：① `handle_message` 工具跑完后**重读当前 session**，agent 回复写进**新** session（旧实现写进旧 sid，一刷就丢）；② **agent 工具在对话中触发版本变更 → 跳过 `persist_opening`**（§11.8），用 agent 自己那句当新 session 引导（更贴 + 省一次 LLM）；UI 按钮触发（无 agent 在场）→ 保留 `persist_opening`（§11.8 现状不变）。
5. **主动发现走两档（D5）**：用户明确要求优化 → `suggest_improvements` 一批 3~8 条**直接落待定**；聊着聊着瞟见一处（未要求）→ **口头问一句**「这段没量化，要收进优化点吗？」，点头 → 单条落待定。待定栏只装「用户点过头的东西」，不悄悄加作业。
6. **三道闸防话痨（D6）**：① 不重提——补注入「已拒绝」栏（`pending_suggestions()` 已返回、`_build_system_prompt` 漏拼，真 bug）+ 写死「同一 target 任何栏出现过就不许再提」；② 积压刹车（阈值 5）——待定积压 >5 → 注入提示 + agent 停止提新、改为催办；③ 话题相关——只在用户刚聊到简历那处时就地开口（软，交 agent）。
7. **工具一个不涨（D7）**：`decide_suggestion` 改名 `update_suggestion`，`decision` 枚举加 `discuss`（→正在聊）、`retract`（→回待定），与现有 accept/reject/refine/split 共 6 值 = 面板 4 按钮 + 2 个讨论动作。净账：−1（废 propose_suggestion）+ 1（apply）= 工具数不变，能力翻倍。**最终业务工具 9 个**（`chat_tools.py::TOOLS` 单一真相源）。
8. **废提议卡 + `propose_suggestion` 工具（D8）**：agent 收口讨论时把改法**直接更新到那条建议上**（面板「正在聊」栏立刻显示），聊天纯文字问「我改成了『…』，收进已确认？」。删单例提案 + 6 处 `clear_proposal` + 2 端点 + 1 组件，一整类陈旧 bug 归零。
9. **开始改的提议时机（D9）**：后端注入门控状态（复用按钮判据：待定清零 且 confirmed 非空）。confirmed ≥3 → 主动提议；1~2 → 建议再攒；还有待定 → 不提、先催办。**同一门控状态只提议一次**（提了没接就闭嘴，等新情况）。
10. **面板 → agent 反向链路做到档 0 + 档 1（D10）**：档 0——`_build_system_prompt()` 挪进工具循环内、每次工具调用后重建（修 D2 挖大的「过期面板」坑）；档 1——注入时 diff 上轮 vs 本轮面板，标变化 + 标**谁干的**（用户点的 / agent 自己调的）。**不做**档 2（面板动作写聊天流，污染 + 跟 event 过滤打架）、档 3（面板动作触发 agent 说话，噪音）。
11. **不做手动添加入口（D11）**：聊天是建议唯一入口（想加一条跟 agent 说，它还能补 target/reason/severity；手填表单是让用户干 LLM 的活）。

> **实现状态（2026-08-25）**：设计定稿，待实现。

> **实现状态（2026-08-10）**：落库 + 三栏面板 + 接受/拒绝/聊一聊 + agent 注入面板全貌 + `decide_suggestion` 裁决工具 + apply 应用 confirmed → 新稿。
>
> **2026-08-12 实现**：四栏（加已拒绝灰栏）+ 撤回 + 默认展开 + 角标优先级级联 + 开始改门控 + 偏好延迟记录 + 版本变更统一结清（保留 discussing）。
>
> **2026-08-13 实现**：左右 1:1 + 加宽 880px + 统一建议卡（原文划线 → 新改法）+ 删头部总数 + `propose_suggestion` 工具 + 聊天内提议选项框（收进已确认 / 继续聊）+ **滚动修复 + 卡片收起/展开**（待定默认展开、右三栏默认收起可手动点开）。

### 12.4 确认后改写：文档任务增量改写 + 固定模板重渲染（**2026-09-09 并入统一简历图**）

**决策：用户确认建议后，由文档任务（非对话 agent）基于当前文档 vN + 选中的建议，增量改写结构化内容 → 重渲染 HTML → 人门预览确认 → vN+1。应用完成 = 版本变更 = 开新 session。**

- **只动选中的部分，没选的保留原样**——用户对照 vN 看 vN+1 改动清晰（1.2 target 精确定位）。
- 增量改写（而非从事实库重新组合）的理由：轻量、不依赖完整生成能力（暖态走 `edit_json`，冷启动才从 facts 重组，§13.4）。
- **渲染**：内容层由固定模板（Jinja2）确定性重渲染 HTML（§13.3）——排版不再是 LLM 的活，内容变了就重渲染。
- **走统一图 + 人门（2026-09-09）**：「开始改」把已确认建议渲染成文本进 `user_request`，进统一简历图 → 机器门 + 人门预览确认 → 确认才落库。**不再走 `POST /optimization/apply` 直接落库**（该端点已删）。
- **确认后才改**：`target` 精确落点，避免误伤。
- 产出进版本化预览（vN+1，§9bis），用户左栏对照看效果（iframe 显示渲染层）。
- **apply = 版本变更 = 开新 session**（决策三）：应用完成即版本变更，开新 session、UI 段落分隔（§11.1）。"新简历就是新的开始"，用户看到清晰的轮回感。

### 12.5 拒绝记忆

**决策：拒绝记录**（"拒掉这一类"，如 `{type:'reject_quantify'}`）**延迟到版本变更时记**（2026-08-12 策略反转）——拒绝不即时记偏好，因为拒绝可撤回（灰栏），撤回后不算"这一类"；到版本变更统一结清清空 rejected 时，按**最终仍被拒的类别**聚合记偏好，以后同类不再建议。

- 记的是"这一类"（用户对判定标准的个人意志，§5），**不是**具体某条建议——拒"量化"就记住"后端成就不可量化"，同类不再建议。
- 偏好独立于事实库（§5：聊出来→确认→持久化→设置页可编辑），生命周期同事实。

## 13. 生成流水线（1.3）

> 2026-08-06 grill 定稿；**2026-08-12 入口收敛到聊天**：删掉空态「生成简历」按钮 / 工具栏 Sparkles / 目标岗位表单——生成整份简历**完全走聊天**（agent `generate_resume` 工具触发），目标岗位自然聊出存 fact。一阶段/二阶段分离（见下）。

### 13.1 流程总览

```
[对话 agent·采集姿态] 信息收集到成熟（用户"帮我生成一份简历" → agent 调 generate_resume 工具）
   ↓
[目标岗位] 不前置填表——聊天里自然聊出（agent 问"打算投什么方向？"）→ 存 fact（§13.2）
   ↓
[文档任务·整份生成] 从 active facts 取材组合 → 结构化 resume JSON → Jinja2 固定模板渲染 HTML（§13.3）
   ↓
[暂存预览态] 产出先暂存（不写库，覆盖式）→ 左栏预览；不满意**重新生成**（覆盖暂存，不堆版本）
   ↓ 用户确认
[确认入库] 写库 vN（版本变更）→ 开新 session（§11.1）→ 试衣间（二阶段）待二阶段实现
```

> **页数（2026-08-28 修订）**：不再是「生成时锁死一页」——排版由固定模板 + 字号阶梯（`Typography` 四参数）人工调，页数靠 A4 纸逐页预览人眼定。

### 13.2 目标岗位

**决策：不设前置表单**（2026-08-12 修订）——目标岗位是用户事实，聊天里自然聊出（agent 采集姿态会问"打算投什么方向？"）存 `user_facts`（basic 类），生成时自动带上；没聊过则基于事实库生成通用版。**岗位进事实库**（决策六）：目标岗位是用户事实，不是只存生成上下文的一次性输入——1.2 的 `job_relevance`（岗位相关性）建议也要用它，全局共享。
- **单值槽位**（2026-08-07 定稿）：目标岗位是"同时只有一个当前值"的槽位——不同的旧目标岗位先标 superseded（留 history）再写新岗位；同岗位幂等跳过（不堆重复 active 行）。通用冲突检测对"目标岗位：X"看不出槽位级冲突（共享前缀稀释相似度 < 0.8），故槽位逻辑在 `save_target_role` 显式处理。对话链路聊出的目标岗位 `source=chat`。
- **agent 生成工具**（2026-08-12）：`generate_resume` 工具（`chat_tools`）——用户聊天明确要求生成时调用，复用 `generate_preview`；`/chat` 响应带 `preview_pending`，前端拉 `GET /resume/generate/preview` 显示 + 「确认保存」悬浮条（确认走 `/resume/generate/confirm`）。

### 13.3 产物链：结构化 JSON 内容层 → HTML 渲染快照 → PDF（**2026-08-28 排版转向**）

> **本节整体重写。** 旧版（2026-08-13「Markdown 内容层 → LLM 排版 agent → HTML 排版层」+ 2026-08-13「Playwright 排⻚闭环」）已被  推翻——见本文件末尾变更记录「2026-08-28 排版转向」。

**决策（2026-08-28，grilling 定稿）：LLM 从「排版 + 排⻚」彻底退出。内容结构化（JSON），排版用固定模板（Jinja2）确定性渲染，页数靠字号阶梯 + A4 纸逐页预览人工调。**

```
上传 → 抽取 → user_facts（半结构化 JSON，分散原料）
                  ↓ 生成（LLM，结构化输出）
        resume JSON（JSON-Resume 词表 + layout 映射表，整体成品）
                  ↓ 渲染（Jinja2 确定性，后端纯函数）
        HTML（每版冻结快照）→ 前端 iframe A4 纸逐页预览 + 字号阶梯缩放
                  ↓ 打印
        PDF（导出层）——已实现（Electron 隐藏窗口 printToPDF）
```

**核心不变量：`HTML = render(resume_json, typography)` 是纯函数。** 同样输入永远同样输出，内容与排版永久解耦——「排版崩了 / 内容被吞」这类事结构性消失。

- **为什么 LLM 退出排版**（推翻旧 §13.3「HTML 由 LLM 生成而非固定模板」）：LLM 自由排版带来「每份简历独一无二的版式」，但这个自由度恰恰是三类 bug 的温床——① 排⻚闭环删 HTML 内容但从不回写 Markdown（Markdown 与 HTML 分叉，内容静默丢失）；② `shell_html` 剥 body 时丢掉 `<head><style>`（排版乱）；③ `.a4-sheet` 每轮重套一层壳（嵌套）。对单用户求职产品，「确定性、内容不丢、排版不乱」远重于「版式唯一」。
- **三列并存**（`resume_documents`，详见 DATABASE.md）：`markdown`（上传 v1 的 MarkItDown 抽取物 + 元件兜底预览）、`resume_json`（生成版结构化真身）、`html`（生成版渲染快照）。上传 v1 只有 markdown；生成版只有 `resume_json` + `html`（`markdown` 空）。
- **渲染层是纯函数**（`app/services/render.py::render_resume`）：不碰 DB、不知道 LLM 存在；模板 + CSS 惰性单例编译，per-request 无文件 IO。方位（header/left/right）由 `layout` 映射表决定——调顺序 = 改 layout 数据，不动模板。
- **排版自由度（2026-09-02 扩）**：排版参数从单一 `scale` 扩成四参数 `Typography`（字号 / 行距 / 段距 / 字间距），一体注入模板 `:root` CSS 变量（`--scale/--lh/--spacing/--ls`）。落库挂版本（`resume_documents.scale`），新生成稿继承上一版。
- **前后端分工**：前端 iframe + `sandbox` 渲染落库 HTML（CSS 不污染应用外壳、禁脚本），**不新增后端 HTML 端点**。
- **PDF 导出（已实现）**：左栏「下载」菜单（PDF/Markdown/HTML）→ Electron `resume:export` IPC；PDF = 隐藏窗口 `printToPDF` 矢量直转（不截图）。PNG 已砍（2026-08-31，PDF 够用）。
- **「内容永不丢」从口号变机器断言**：① 生成层——每个 active fact 被某个 block 覆盖，LLM 漏了立刻报；② 渲染层——模板确定性遍历全部字段，字段在内容里就一定渲染出来。

### 13.4 编辑流水线：对话 agent 路由 → 统一简历图（人门确认）（**2026-09-09 收敛，**）

> **本节整体重写。** 旧版（2026-08-13「双模式编辑流水线」`classify→content→layout→validate` + Playwright 排⻚闭环）已被  相继取代——`layout` 节点随 LLM 排版一起删，排⻚闭环全废。

**决策（2026-09-07 合并 + 2026-09-09 并入「开始改」）：生成、改写、「开始改」收敛为同一条流水线——「出草稿 → 机器门自愈 → 人门确认 → 落库」。**

```
用户请求（生成 / 改简历 / 开始改）
  → 【对话 agent = 前台接待员】路由，不自己干重活（§11.4）
  → 【统一简历图】入口判冷 / 暖
       冷（无当前 JSON）→ facts → generate_json_from_facts
       暖（有当前 JSON）→ edit_json（增量改写）
       → content ⇄ validate_content（机器门，MAX_ITERATIONS 兜底）
       → layout（Jinja2 确定性渲染 HTML，非 LLM）
       → human_gate（interrupt() 挂起，checkpointer 持久化、重启不丢）
  → 人确认 → 落库 vN+1 → 版本变更 → 开新 session
  → 人带意见重改 → 回 content 重改（不落库）
```

- **机器门（`validate_content`）**：确定性校验「每个 active 且 `on_resume` 的事实都在成品里」。漏了沿 `content_problems` 喂回 `content` 自动补（`MAX_ITERATIONS=3` 兜底），**不需要人**。只拦「整条事实连影子都没进成品」的硬丢失；软质量（措辞 / 量化够不够）是 LLM 的活，不归它。
- **人门（`human_gate`）**：草稿渲染好后人拍板——`confirm` 落库 / `revise` + feedback 回 `content`。用 `interrupt()` 挂起，和机器门（确定性、无人）是两道性质不同的门。拍板走独立 UI + 端点（`POST /resume/generate/confirm`），**不进聊天循环**。
- **编排检查点**：`AppError` 挂起态存 `checkpoints.db`（独立文件，`app/graphs/checkpoint.py` 装配 `AsyncSqliteSaver`），与业务库分离；`thread_id` 按 `{graph}:{scope}` 派生（单用户单值）。
- **冷启动不死锁**：无结构化 JSON 时「开始改 / 改简历」不再抛死路——冷启动走 facts→生成第一版（请求作改进要求注入）；暖态增量改写 + facts 只补缺口（JSON 权威、不覆盖手工改过的措辞）。共享核心抽在 `services/resume_edit.py`（`generate_json_from_facts` / `edit_json`）。
- **「开始改」并入**：已确认建议渲染成文本进 `user_request`，走同一条图的机器门 + 人门预览确认，不再 `POST /optimization/apply` 直接落库。
- **服务层 `app/services/rewrite.py`**：调图编排 + 机器门 + 写库（`resume_json` + `html` 双写）+ 版本变更统一结清 + 开新 session。
- **对话 agent 工具**：`generate_resume` 单一工具（不再区分生成 / 改写），只做路由——真正的生产在文档任务里。
- **与 1.2 分工**：文字优化走建议流（`suggest_improvements` → 面板确认 / agent 操作 → 开始改），最终也汇入这条统一图。
- **上传 v1 的处理**：上传 v1 是 markdown（原生元件预览兜底），还没有 `resume_json`；首次生成 / 改写 = 把 facts 组合成 JSON，天然是冷启动。

### 13.5 整份一次出

**决策：生成整份一次出，不分节。**

- 简历几千字，LLM 整份读入无压力（§1 已论证）；分节出"拼接"反而易出结构错乱。
- 从 active facts 取材组合，产出落左栏预览。

### 13.6 直接产出，暂存预览，确认才入库

**决策：产出先暂存（预览态，不写库）→ 左栏预览 → 用户确认才入库。**

- **产出暂存，不写库**（决策二）：生成结果先落在预览态（不占 `resume_documents` 版本）；不满意**重新生成**（覆盖暂存），不堆垃圾版本（vN、vN+1、vN+2…）。**确认后才写库** → 版本变更 → 开新 session。
- **「重新生成」= 人门 revise**（2026-09-08）：意见**可选可空**——空 = 整份重来，填了 = 定向重改。revise 回图重改、仍在人门挂起（**不写库**，`version` 返回 null）。这条回边跑在 chat 循环之外，停它走独立端点 `POST /resume/generate/stop`。
- **挂起态抗重启**：草稿存 checkpointer（`checkpoints.db`），重启后按派生 `thread_id` 查回——不再依赖内存单例。
- 不满意：**重新生成**（覆盖暂存）或走 1.2 优化流 / §9bis 回滚（版本化是安全网）。
- **生成确认 = 版本变更 = 新 session 轮回**（§11.1 闭环）：用户确认生成结果后进入下一版本周期。
