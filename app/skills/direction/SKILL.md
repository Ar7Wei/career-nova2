# 求职方向：提炼 / 落定 / 查市场

这是"方向"的领域规则——方向是决策，人拍板，不自动改写。

## refine_direction（出提案，不落库）

当聊出了求职目标（岗位/城市/技能方向）时调用，提炼方向提案给用户看。
- 本工具**只产提案、不落库**——调用后把提案（岗位/城市/搜索词）讲给用户听，问 ta 认不认。
- 提案只是转述原料，不产生界面卡片；用户拍板前**不要**调 commit_direction。

## commit_direction（人拍板后落定）

仅当用户明确确认方向改动（"就这个""改成后端吧""可以，定了"）时调用，把方向写回 facts。
- role：目标岗位标签（写简历/展示用，不参与搜索），可空。
- keywords：二维查询组（组内多词、组间 OR），只管搜索，上限 6 组。
- cities：城市数组，**与 keywords 平行等长**（`cities[i]` 是第 i 组要搜的城市），逐组必填，
  只支持 25 城白名单（见下「城市挂到组上」）。
- 用户犹豫/讨论时不要调——先用 refine_direction 出提案。

### 城市挂到组上（2026-09-13，ADR 0019）

**城市属于每个查询组，不是方向级的一个值。** `["Java","后端"]` 可以配成都、`["产品"]` 配杭州，
各搜各的——因为抓取的天然单元就是「一组词 + 一个城市」。

- **逐组必填**：每个组都要有一城市，没有「全国」「不限」——前程无忧留空 = 回落用户 IP 城市，
  语义是坏的。
- **定位准**：一句话收口「这些组都按杭州搜？」→ 所有组填同一个城市。
- **定位散**：逐组问「前端那条配杭州、产品那条你想到哪个城市？」→ 分别填。
- **没有证据时留空**（refine 阶段 `cities[i]=""` 允许），**绝不编造城市**——留空就当面问用户，
  问清了再 commit。commit 时还空着会被挡回。
- 数组长度必须和 keywords 一致；落定前后端会校验 `len` 相等 + 逐项白名单。

### 用户还没想清城市怎么办（**别逼他先定，也别上来就全国撒网**）

用户说「城市不确定 / 哪座城机会多我去哪」时，**不要**先卡在「请先确认城市」——那啥都干不了。
按这个顺序走：

1. **先 grill 两问**（比任何数据都准）：
   - 你 base 在哪座城？（眼下住哪 / 家在哪 / 有没有必须留下的原因）
   - 如果只让你在 3~5 座城里挑，你会留哪几座？
2. **候选城逐城查**：拿圈出的城市**一城一调** `query_market`，比真实薪资段 / 经验门槛 / 岗位规模。
3. **结合常识讲**：拿数据 + 你对城市岗位密度的常识，讲出「哪座城对你更划算」，用户拍板。
4. **兜底**：真圈不出（"哪都行"）→ 才用**全国查询**（`cities` 传空）瞄一眼，从真实岗位看哪些城
   反复出现，回头再圈。**全国查询是兜底，不是默认路径。**
5. **定了再 commit**——探索期只 refine 不落定。落定会触发后台抓取，把没选中的城的岗位一起抓进库。

**比城市 = 一城一调**（工具不替你比）：
`query_market([["前端"]], ["北京"])`、再 `query_market([["前端"]], ["上海"])`——拿两份快照自己比。
**不能一次传多城**：一次调用只吐一份**合并**统计，多城混一起就看不出城的差别了。

**岗位规模估值怎么读**（返回里的「岗位规模」）：那是猎聘给的数，**封顶在约 800**——
`昆明约 224` 这类**低值可信**（说明这城岗少）；大城市全压在封顶线上（北京 801 / 成都 800），
**互相不可比**。**只看「哪些城明显偏小」，别拿 801 和 800 比大小。**


### keywords 检索词写法（**实测平台检索语义**，ADR 0018）

> 下面不是凭空规定，是 2026-09-11 对猎聘 / 前程无忧搜索框实测出来的行为。写词前先读懂。

**平台的真实行为（三条）**

1. **自适应 AND**：一条查询里的多个词，**有交集时按 AND 算**（交集够大时基本全命中）；**交集不足时静默放宽成 OR**——返回只满足其中一个词的结果。
2. **变体容忍**：平台自己会做变体匹配——搜 `vue` 一次就同时覆盖 `vue2`/`vue3`/`vue.js` 的岗位。
3. **放宽留哪个词不可控**：退化时保留哪个词**跟词序无关**，我们控制不了。

**由此推出的写法**

- **一组 = 一个概念 + 一个与它大范围共现的收窄词**。收窄词要和概念词**大量同时出现**，AND 才会生效。
  - 正例：`["Vue","前端"]`（Vue 岗绝大多数是前端岗，交集大，AND 生效）。
  - 反例：`["Vue","招聘专员"]`（交集极小 → 静默退化成搜 "Vue"，你以为在收窄、其实没有）。
- **同义词/变体只留最强的那个，绝不堆一组**。写 `["vue","vue3","vue.js"]` 是白费功——平台自己会扩；堆了反而稀释。
- **不要用低共现词当收窄条件**——那是最危险的写法：看着像收窄，实际退化成单词查询，且**你察觉不到**（响应不给命中总数）。
- **组数：2~3 组起步**（上限 6）。一上来别顶满；等岗位变少、不够用了再慢慢扩组。
  - 推荐配比：**兜底线 1 组**（纯岗位名，捞标题不写技术的岗）+ **内容线 1~2 组**（核心技术/工作内容）。
  - 为什么两条线都要：搜技术词准但漏（标题常不写技术），搜岗位名全但杂。互补，不是二选一。
- 组间 OR：每组各搜一遍、结果按 external_id 合并去重。
- 岗位名要参与搜索，必须在 keywords 里显式加一组——role 不参与搜索。

**别这样（负例）**
- `[["vue","vue3","vue.js"]]`——同义变体堆一组，平台自己会扩，无用功。
- `[["Vue","招聘专员"]]`——低共现收窄，静默退化。
- `[["前端"],["后端"],["测试"]]`——每组一个岗位名的并列是三个不同方向，不是一组搜索策略。

## query_market（现场查市场 + 验自己的词）

方向是第一优先要聊透的事，市场数据是方向决策的证据——查市场不是用户点名才做，是对的时候主动做。

**主动查的时机：**
- 聊到候选岗位、还没数 → 主动查，用真实岗位量告诉 ta 哪边肉多。
- **关键词快聊定、准备提提案前 → 必查一次，验这组词到底召回了什么**（见下）。
- 用户踌躇选不出方向 → 给一份市场视野（各方向量/门槛对比），帮 ta 破僵局。

**怎么用返回里的「每组召回诊断」验词：**

工具每组给的是**原始计数**（每个词标题命中几条、全部词同时命中几条、几条样本标题）。判断归你：

| 读数 | 含义 | 你该做的 |
|---|---|---|
| 「全部词同时命中」≈ 最大单词命中 | **AND 没生效，退化了**——这组其实在按单词搜 | 换收窄词（换成与概念词共现更多的），或拆组 |
| 「全部词同时命中」明显低于最大单词命中 | 收窄在起作用 | 可以 |
| 某词标题命中数极低 | 召回的要么是噪音、要么词太窄 | 换更通用的词（变体不用列，平台会扩） |
| 样本标题里混进不相关岗位 | 放宽产物 | 酌情收紧 |

**怎么验「我简历里的这个词，能不能当收窄词」**（把硬编码规则变成现场数据）：
收窄词从**用户简历**里来（他的第二技能：TypeScript、小程序、Webpack…），不是从市场捡词。
但它**跟概念词的共现够不够是市场事实，简历答不了**——查一次就知道：
把候选收窄词和概念词组一组查，读两个词的 `标题命中数`——
- 两者**接近**（如 `Vue 12 / 前端 13`）→ 共现强，AND 会生效，是好收窄词。
- 收窄词**远低于**概念词（如 `Java 0 / 前端 40`）→ 共现弱或没有，配进去**必静默退化**成单词搜。
  这还是个**双信号**：不只说明配对不行，也说明**简历跟这个市场错位**（他以为值钱的技能，这市场不认）。

> **边界（2026-09-13）**：上面这些「标题命中」只用来判断**这组词写得对不对 / AND 有没有生效**——是**代理指标**，不是检索词优劣的证据。**别拿它给检索词的好坏下结论**：命中可能发生在 JD 正文（岗位标题不含、正文含），而我们只数得到标题；平台恒返固定条数也没有判别力。检索词的真实好坏**只能由投递反馈回头验**（哪组词捞回的岗位真被投/进面），那不在本工具能力内——别向用户承诺"这组词更好"。

**怎么用返回里的「岗位规模」验市场大小**（ADR 0020，实测）：那是猎聘给的数，**封顶在约 800**。
`昆明 224` 这类**低值可信**（这城/这方向岗就是少）；大城市全压封顶线（北京 801 / 成都 800），
**互相不可比**。**只看「哪些明显偏小」，别拿 801 和 800 比。**


**节流（别查滥）：** 现场查猎聘慢且触发风控——同一个方向查一次就够，别用户每改一个词就重查。

**怎么讲：**
- 带参数查：把用户说过的候选方向（查询组 + **逐组城市**，与 commit 同构的平行数组）直接传，
  不必等方向落库；每组各查各的城市。
- 你做判断：拿数字比对 facts（经历/技能/学历/年限），讲出「用户 vs 市场」差距，带理由、带差距、带风险。
- 诚实标注：样本仅猎聘，讲的时候明说"按猎聘来看"。
- 不硬编：查询失败如实告诉用户，别编市场数字。
- 不是结论：市场是证据，方向定不定最终用户拍板。

## 常见坑

- 用户犹豫时就 commit（应该先 refine 出提案等人拍板）。
- 同义变体堆一组（平台自己会扩，白费功）。
- 用低共现词收窄（静默退化，你以为在收窄）。
- 一上来就顶满 6 组（2~3 组起步，岗位少了再扩）。
- 用户想要多城市时硬塞一个 city 串（应逐组配城市，见上）。
- **城市不定就卡住问城市**（该先 grill base + 圈候选城，再逐城查，见上）。
- **一次 query_market 传多城想对比**（一次只吐一份合并统计，看不出城的差别——要一城一调）。
- **拿 801 和 800 比城市大小**（那是猎聘的封顶估值，只在明显偏低时可信）。
- 反复查同一批关键词触发风控。
